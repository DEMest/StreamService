# Контракт API: правила для сайта и приложений

У API два клиента: сайт (`apps/web`) и нативные приложения. Сайт выкатывается
вместе с API, а приложение из стора — нет: выпущенную версию нельзя обновить
принудительно, и она ходит в API месяцами. Поэтому контракт описан машинно, а
менять его можно только по правилам ниже. Требования — `docs/srs.md`, NFR-48 и
NFR-52; задача — #129.

## Где лежит контракт

| Что | Где |
|---|---|
| Описание в OpenAPI 3, генерируется из кода | `apps/api/openapi.json` (в репозитории) |
| То же в рантайме | `GET /v1/openapi.json` (через сайт — `/api/v1/openapi.json`) |
| Типы сайта, генерируются из описания | `apps/web/src/lib/api-schema.ts` |
| Механика: ошибки, валидация, курсор, сборка документа | `apps/api/src/common/api/` |

Обновить оба файла после правки эндпоинта:

```bash
pnpm api:contract
```

Руками их не правят. Отставший `openapi.json` роняет тест
`common/api/openapi.spec.ts`, отставшие типы сайта — шаг CI в джобе web.

## Как писать эндпоинт

Так написан пилотный эндпоинт: `apps/api/src/search/` (`search.dto.ts`,
`search.controller.ts`).

1. **На контроллере `@ApiTags('…')`.** Без тега эндпоинта нет в контракте.
   Тест `openapi.spec.ts` падает на новом контроллере без тега, а также на
   эндпоинте контракта, у которого ответ или тело не описаны классом.
2. **Запрос описывается классом с декораторами class-validator и `@ApiProperty`:**
   `@Body() dto: CreateEventDto`, `@Query() q: EventsQueryDto`. Глобальный
   `ValidationPipe` проверяет его и отвечает `400 VALIDATION_FAILED`.
   Незнакомые поля молча отбрасываются (`whitelist`), до сервиса доходят
   только описанные. Число из query приходит строкой, поэтому ставьте
   `@Type(() => Number)`.
   **Не используйте `@Query('x') x?: number` и `boolean` по старинке.** Пайп
   работает с `transform`, и такой параметр без значения приходит `NaN`
   (`boolean` — `false`). Повторённый `?x=a&x=b` в `string` склеивается в
   `"a,b"`. Параметры описываются классом.
3. **Ответ описывается классом с `@ApiProperty`.** Метод контроллера объявляет
   его типом результата (`Promise<SearchResultsDto>`), а сервис возвращает
   этот же класс, без второго интерфейса рядом. Тогда описание и настоящий
   ответ не разойдутся без ошибки компиляции. Плюс `@ApiOkResponse({ type })`.
   - `null` в поле — `nullable: true` и явный `type`: из `X | null` TypeScript
     тип не выводит.
   - Момент времени — `type: String, format: 'date-time'`.
   - Целое число — `type: 'integer'`. Без этого генераторы Swift и Kotlin
     получат `Double`.
4. **Ошибки бросаются через `ApiException`:**
   `throw new ApiException(HttpStatus.NOT_FOUND, 'EVENT_NOT_FOUND', 'Турнир не найден')`.
   Описываются через `@ApiNotFoundResponse({ type: ApiErrorDto })` и аналоги.
5. **Адреса медиа выдаёт сервер** (NFR-52): `hlsUrl` и `posterUrl` приходят в
   DTO готовыми. Закрытые потоки — по правилам `stream/stream-access.ts`.
6. **На сайте тип берётся из контракта:** `ApiSchemas['SearchResultsDto']` из
   `@/lib/api`, а не своя копия интерфейса.

Класс-DTO называется с суффиксом `Dto`. Имя класса становится именем схемы в
OpenAPI и именем типа в клиентах.

## Формат ошибки

Любая ошибка, брошенная исключением (`ApiExceptionFilter`), а также 404 на
несуществующий адрес:

```json
{
  "statusCode": 404,
  "code": "EVENT_NOT_FOUND",
  "message": "Турнир не найден"
}
```

- `code` — машинный код, `SCREAMING_SNAKE_CASE`. Конкретный код ставит
  эндпоинт через `ApiException`. Если его нет, ставится общий по статусу из
  явной таблицы в `api-error.ts`: `NOT_FOUND`, `UNAUTHORIZED`,
  `INTERNAL_SERVER_ERROR`…; статус вне таблицы — `HTTP_<n>`. Из фраз
  `http.STATUS_CODES` код не выводится: Node меняет их вслед за RFC.
- Коды самого слоя API: `VALIDATION_FAILED` (с полем
  `fields: [{ field, messages }]`, путь вложенного поля — `venues.0.quad`),
  `INVALID_CURSOR`, `INTERNAL_SERVER_ERROR`. Текст необработанной ошибки
  наружу не уходит, только в лог.
- `message` — для человека. Бывает по-русски и может поменяться. Разбирать его
  кодом нельзя.
- У старых эндпоинтов в теле остаются прежние поля (`error: "Not Found"` от
  Nest). Фильтр только добавляет недостающее.
- **Ответ, который обработчик пишет сам через `@Res()`, фильтр не видит.** Так
  устроена раздача HLS в `RecordingController`: `res.status(404).json(...)`
  уходит без `code`. Новые эндпоинты бросают исключения, а не пишут ошибку в
  `res`.
- **Клиент ветвится по `code`.** Незнакомый код обрабатывается по
  `statusCode`. На сайте ошибка запроса — `ApiRequestError` (`status`, `code`,
  `message`, `fields`). `code` у неё пуст, если ответ пришёл не от API, а
  например от прокси при выкатке.

## Списки — порциями с курсором

Лента меняется, пока её листают, поэтому номер страницы показал бы карточку
дважды или потерял бы её.

- Запрос наследует `CursorQueryDto`: `cursor` и `limit` (по умолчанию 20,
  максимум 100). Умолчание задано в самом классе, так что `q.limit` всегда
  число, и `?? 20` в эндпоинте не нужен.
- Ответ — свой класс-порция: `export class EventPageDto extends CursorPage(EventCardDto) {}`
  даёт `{ items, nextCursor }`. Именованная схема нужна, чтобы в Swift и Kotlin
  получился тип `EventPage`.
- Выборка идёт с `take: limit + 1`, `toCursorPage` отрезает лишнюю строку и
  кодирует позицию последней. `decodeCursor(raw, isPosition)` проверяет форму:
  испорченный курсор даёт `400 INVALID_CURSOR`, а не 500.
- Порядок обязан быть устойчивым. Последний ключ сортировки — уникальный `id`,
  и позиция курсора содержит все ключи сортировки.
- Для клиента курсор непрозрачен: он только передаёт `nextCursor` обратно.
  `nextCursor: null` значит, что дальше ничего нет.

## Время

- **Момент времени** — UTC в ISO 8601 с `Z`: `"2026-12-14T04:12:00.000Z"`.
  Так `Date` и сериализуется. Локальное время показывает клиент.
- **Календарный день** (даты афиши турнира) — строка `"YYYY-MM-DD"`, без
  времени и пояса, `format: date`. «14 декабря» одинаково для зрителя из
  любого пояса. Перевод в эту строку и обратно делает одна общая функция:
  `new Date(год, месяц, день)` вне контейнера API сдвигает день на предыдущий.

## Совместимость внутри `/v1`

1. **Поля только добавляются.** Нельзя переименовать или удалить поле, сменить
   его тип или сделать `null` поле, которое раньше всегда было заполнено.
2. **Клиент пропускает незнакомые поля и незнакомые значения перечислений.**
   Для каждого перечисления в описании поля сказано, как показывать
   незнакомое значение. Например, неизвестный статус схватки клиент показывает
   как `waiting`.
3. **Новые поля запроса — необязательные.** Старое приложение их не пришлёт.
   Незнакомые поля запроса сервер отбрасывает, а не отвечает ошибкой.
4. **Ломающее изменение — новый эндпоинт** (или `/v2`). Старый живёт, пока в
   него ходят версии приложения из сторов.
5. **Приложение передаёт свою версию** в заголовке `X-Client-Version`:
   `ios/1.4.0`, `android/1.4.0`. Сайт заголовок не передаёт. В контракте он
   описан как общий параметр, чтобы попасть в клиенты с первой сборки.
   **Сервер его пока не читает и не пишет в лог.** Учёт версий, чтобы
   понимать, когда старый эндпоинт можно выключать, — отдельная задача.

## Что не входит в публичный контракт

`/v1/openapi.json` открыт без авторизации, поэтому маршруты под
`/v1/admin` (API админки, на основном домене nginx отдаёт его как 404) и
`/v1/internal` (вебхук и авторизация MediaMTX) в документ не попадают, даже
если описаны по правилам. Список префиксов один — `NON_CONTRACT_PREFIXES` в
`common/api/openapi.ts`, им же пользуется проверка в `openapi.spec.ts`.
Эндпоинты админки всё равно пишутся классами с валидацией. Типы для страниц
админки сайт пока пишет сам, пока не понадобится отдельный документ.

## Старые эндпоинты

Эндпоинты, написанные до этих правил, описаны интерфейсами, которых в
рантайме нет. Поэтому их нет в контракте, а валидация их не трогает. Список
таких контроллеров — `LEGACY_CONTROLLERS` в `common/api/openapi.spec.ts`. Он
только сокращается: контроллер, который заново описали по правилам, получает
`@ApiTags` и уходит из списка. Вне контракта навсегда остаётся `/health`
(список `NOT_FOR_CLIENTS`).
