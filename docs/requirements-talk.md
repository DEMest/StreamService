# Требования к продукту — сопроводительный документ к выступлению (7 минут)

Рабочий документ команды для выступления «требования к разрабатываемому
программному продукту и почему они именно такие». Источник истины по
продукту и архитектуре — [`vision.md`](vision.md) (исправлен вместе с этим
документом); здесь — выжимка для речи, разбор пожеланий заказчика и план
на 7 минут.

---

## 0. Рамки: о чём говорим и с каким фокусом

Говорим обо всём, что входит в продукт, но с разным фокусом.

| Тема | Фокус в выступлении |
|---|---|
| Нагрузка, разделение на сервисы, наблюдаемость, CI/CD, стенды, CDN, несколько медиа-серверов | **Основной.** Это ядро работы команды на предмете |
| Функции организатора: событие, пульт, секретарь, автонарезка | **Основной.** Создают сценарии и нагрузку, под которые строится всё остальное |
| Приложение зрителя (iOS/Android) | Упоминаем: делается параллельной командой того же состава; с нашей стороны — контракт API, лента клипов, push, подписки |
| Приложение организатора (по образцу Mevo: NDI-камеры, пульт, плагины) | Упоминаем: сторонняя задача, решается параллельно; с нашей стороны — ингест нескольких потоков и API пульта |
| AI-комментатор | Упоминаем как направление целевой архитектуры |
| Платные подписки зрителя через ЮKassa | Упоминаем как возможный отдельный этап; состав подписки определяется с заказчиком |
| Сроки | Называем порядок этапов и зависимости, без дат: оценка делается по согласованным юз-кейсам |

## 1. Контекст в двух абзацах

**Что есть.** Liga Live (liga-live.ru) — работающая платформа трансляций
спортивных турниров. Организация (федерация, клуб) подключает свой
видеомикшер по SRT или RTMP. Зритель смотрит в браузере без регистрации,
сам переключает камеру, пишет в чат, пересматривает и скачивает запись. Есть
кабинет организации, приватные эфиры по ссылке, архив в S3, админка, экран
ёмкости, CI/CD с автодеплоем под живым эфиром. Всё работает в продакшне на
одном сервере.

**Ключевое решение, на котором стоит продукт:** сервер никогда не
пересобирает и не разрезает входящее видео, компоновка — у зрителя.
Организация может прислать один композитный поток (мозаика 2×2 из vMix) и
зритель вырежет нужную четверть на устройстве, а может прислать четыре
потока и больше — по одному на ковёр — и зритель смотрит любой отдельно или
все вместе в раскладке на одном экране. Организации это даёт канал под
трансляцию вместо отдельной трансляции с режиссурой на каждый ковёр,
платформе — инфраструктуру на порядок дешевле, чем у конкурентов. Все
дальнейшие требования это решение **сохраняют**; меняются доставка, разрез на
сервисы и наблюдение за ними.

## 2. Откуда берутся требования (источники)

1. **Заказчик** — руководитель организации, проводящей турниры по борьбе и
   транслирующей их на платформе. Просит: пульт организатора, модуль
   секретаря турнира, автоматическую нарезку схваток, мобильный клиент для
   зрителей, приложение-пульт с NDI-камерами, рост аудитории.
2. **Зрители** — родители спортсменов, тренеры, болельщики. Гипотезы H1–H3
   и портреты из отчёта по заданию 1: неудобно переключаться между эфирами
   ковров, пропускают начало схватки, не могут найти запись конкретной
   схватки. H1 и H3 подтверждены заказчиком и опросом его зрителей; живые
   интервью впереди.
3. **Рынок** — VK Видео и WrestlingTV: отдельный эфир на каждый ковёр, нет
   самообслуживания, YouTube в РФ недоступен. Свободная ниша —
   самообслуживание для региональных и детских турниров с выбором камеры у
   зрителя.
4. **Границы текущего решения** — раздел 2.6 `vision.md`: потолок по
   зрителям задан каналом одного сервера (~250 при обычном миксе качеств,
   расчёт), API сам раздаёт видео, монолит с разными профилями нагрузки,
   одна точка отказа, наблюдаемость только продуктовая.
5. **Учебная задача предмета** — показать работу с нагрузкой и инструментами
   командной разработки на реальной системе с живыми пользователями.

## 3. Требования и почему они такие

### 3.1 Неизменяемые ограничения (архитектурные инварианты)

| Требование | Почему |
|---|---|
| Сервер не пересобирает и не разрезает видео; компоновка на клиенте — кроп квадранта или раскладка нескольких потоков организации | Экономическая основа продукта: один канал с арены, N зрителей = N декодирований тех же потоков, что пришли с площадки, никакого серверного транскода основного фида. Конкуренты требуют канал и человека на каждый ковёр |
| Зритель смотрит бесплатно и без регистрации; подписка — добровольное дополнение | Аудитория — то, ради чего организация приходит на платформу; обязательный платный просмотр её сократил бы (бизнес-модель B2B из отчёта) |
| Платформа не привязана к виду спорта | Стартовая ниша — борьба, но ни одна сущность системы не знает про ковры; это расширяет рынок без переделки |
| Работает на российской инфраструктуре, без VPN, на мобильном интернете | Портреты зрителей: Android среднего класса, 4G, YouTube недоступен |
| Изоляция организаций в общей платформе | Многоарендность: чужие данные не раскрываются даже фактом существования (404) |
| Выкатка под живым эфиром не рвёт приём | Турниры идут по выходным, релизы — каждый PR; «не выкатывать во время эфира» — не вариант |

### 3.2 Функциональные требования — что просит заказчик

Формулировки наши (раздел 3.7 `vision.md`); каждый пункт подтверждаем с
заказчиком лично на юз-кейсах, а не по пересказу.

| Требование | Почему |
|---|---|
| **Событие (турнир)**: название, дата, число ковров; трансляции, записи и клипы привязаны к событию | Сейчас есть только Stream и эфир; без события нет расписания, поиска по турниру и привязки схваток |
| **Пульт организатора**: создать событие, выдать ключи ингеста, видеть статус источников, старт/стоп эфира — на одном экране в веб-кабинете и в приложении организатора | Организатор управляет эфиром, не отвлекаясь от площадки; сейчас для этого нужно открыть несколько страниц у ноутбука с микшером |
| **Модуль секретаря**: фамилии и регионы, счёт, нарушение, «начало/конец схватки» ставят таймкоды; работает удалённо | Таймкоды — вход для автонарезки и поиска по спортсмену; секретаря на площадке может не быть. Интеграция с «Ареной» и «Истоком» — вторым этапом |
| **Автоматическая нарезка схваток**: по таймкодам сервер вырезает фрагмент из готовой записи, накладывает фамилии и счёт, публикует клип в ленту и архив события | Главная боль зрителя H2: «не могу найти запись конкретной схватки». Клипы — контент ленты в приложении зрителя. Режется запись, не эфир — принцип сохранён |
| **Справочники**: организаторы, секретари, спортсмены | Нужны секретарю (ввод), поиску (по спортсмену), нарезке (подпись клипа) |
| **Единое API для всех клиентов**: веб, приложение зрителя, приложение организатора | Приложение зрителя делает параллельная команда — ей нужен готовый контракт: каталог, событие, клипы, поиск, push «эфир начался», подписки |
| **Приложение организатора** (по образцу Mevo): NDI-камеры в одной сети, сборка картинки на площадке, отправка на платформу, пульт эфира, встроенный секретарь, **плагины** к трансляции (апскейлинг и другие — набор определяется с заказчиком) | Заказчик хочет управлять трансляцией как пультом, не отвлекаясь. Компоновка остаётся до сервера; плагины — там же, где картинка собирается |
| **Приложение зрителя**: каталог, поиск, плеер с выбором камеры, лента клипов, чат, подписки на организации с push; платная подписка через ЮKassa как возможный этап | Зритель уже приходит с телефона; уведомление о начале эфира и лента клипов закрывают H2 |

### 3.3 Нефункциональные требования — ядро предмета

| Требование | Что сейчас | Почему именно так |
|---|---|---|
| **Масштаб по зрителям**: 2 000 одновременных на эфир и 10 параллельных эфиров на первом шаге, 10 000+ с CDN | ~250 на сервер при обычном миксе качеств, 90 если все смотрят оригинал — расчёт по каналу, не измерение | Рост аудитории — цель заказчика; одного сервера не хватит на первый крупный турнир |
| **Доставка видео не через API**: сегменты в origin-хранилище, зрителям раздаёт nginx/CDN; приватные — подписанный URL | API отдаёт каждый сегмент с локального диска; рестарт API — пауза ~5 с | Единственное изменение, которое одновременно снимает нагрузку с API, делает его stateless и открывает путь к CDN |
| **CDN перед origin** | Нет | Кэш выносится к зрителю, исходящий трафик — в сеть провайдера; это и есть «покупка нагрузки» |
| **Несколько медиа-серверов**: приём и лесенка на выделенных узлах, входящие потоки организаций делятся между ними | Всё на одном хосте, ~7 ядер CPU на один 4K-эфир | Параллельные турниры и организации с четырьмя и более потоками упираются в CPU одного хоста; добавление узла = +N эфиров |
| **Стабильный адрес ингеста** | Есть | Реквизиты в микшере и в приложении организатора не должны меняться при переезде на кластер |
| **Разделение на сервисы по профилю нагрузки**, не по модулям: `ingest-control`, `archive-worker`, `chat-gateway`, `notifier`, `ai-commentary`; ядро — модульный монолит | Один процесс: HTTP, раздача файлов, WebSocket-чат, CPU-тяжёлая склейка, кроны | Режем там, где разные требования к доступности и масштабированию; сервис на каждый модуль — лишние сетевые хопы без выигрыша |
| **Шина событий** (`broadcast.started/ended`, `recording.ready`, таймкоды секретаря) | Вызовы функций внутри процесса | Сервисы не знают друг о друге; нарезка и таймлайн — просто ещё один consumer |
| **Чат и счётчик зрителей вне памяти процесса** (Redis) | В памяти API; второй экземпляр их не увидит | Иначе горизонтальное масштабирование API невозможно |
| **Наблюдаемость трёх уровней**: метрики узлов и контейнеров (Prometheus + Grafana), логи (Loki), ошибки со стек-трейсами и релизом (Sentry), плюс продуктовый экран ёмкости | Только продуктовый экран и QoE плеера; ошибка обнаруживается по обращению зрителя | Нельзя масштабировать то, что не измерено — наблюдаемость **раньше** масштабирования. Единый экран мониторинга по образцу Monium |
| **Нагрузочные тесты как часть процесса** (k6: N зрителей тянут сегменты + M в чате) | Нет | Заменяют расчётный потолок измеренным; гоняются перед крупными релизами |
| **CI/CD**: линтер, e2e на Playwright, проверка миграций, образы по SHA, стенд на каждый PR, GitOps | Сборка и тесты backend, деплой скриптом | Несколько сервисов и несколько клиентов нельзя вести без стендов и воспроизводимых образов |
| **Kubernetes (k3s) как средство, не цель** | Docker Compose на одном хосте | Rolling update, HPA и PDB «не трогать медиа-под под эфиром» из коробки; специфика — UDP-ингест и стабильный IP |
| **Миграции БД отдельным шагом до выкатки** | На старте контейнера | Медленная миграция удлиняет паузу отдачи |
| **Задержка live ~2 с (LL-HLS)** после выноса доставки | Секунды (HLS, сегменты 2 с) | Секретарь ставит таймкоды по живой картинке; чем меньше задержка, тем точнее нарезка |

### 3.4 Процесс: как мы работаем с требованиями

- **Юз-кейсы** — основной формат. Каждый сценарий (организатор создаёт
  событие; секретарь ставит таймкод; зритель ищет схватку; выкатка под
  эфиром; организация шлёт четыре потока) прорабатывается и **согласуется с
  заказчиком** до реализации. Пересказ заказчика, сделанный нейросетью, не
  считаем согласованным — каждый пункт подтверждаем лично.
- Требования живут в репозитории рядом с кодом: `vision.md` — источник
  истины, правится по мере согласования.
- Порядок этапов — по зависимостям: измерить → вынести доставку → кластер
  и сервисы → функции организатора → масштаб; клиенты — параллельно.

## 4. Пожелания заказчика → как мы их принимаем

Пункты из сообщения заказчика. Текст переписан нейросетью, поэтому
принимаем с осторожностью и подтверждаем лично.

| Пункт заказчика | Решение | Комментарий |
|---|---|---|
| Приём SRT и RTMP | Есть | Не переделываем |
| БД профилей (организаторы, секретари, спортсмены), события, привязка видео к событиям | Входит | Раздел 3.7 `vision.md` |
| Единое API для всех приложений | Входит | Контракт для приложения зрителя и приложения организатора |
| Веб-портал организатора: создание события, ключи доступа, мониторинг источников | Входит как пульт организатора | Статус своих источников: онлайн/офлайн |
| Микширование 2×2 на сервере, кнопка «В эфир» | **Переносим в приложение организатора / vMix** | Серверная сборка противоречит основному принципу; собирать на площадке — то же для организатора, но без серверного транскода. Плюс зритель и так может сам скомпоновать несколько потоков. **Подтвердить с заказчиком** |
| Модуль секретаря (фамилии, счёт, начало/конец схватки, удалённо) | Входит | В веб-пульте и в приложении организатора |
| Интеграция с «Ареной», «Истоком» | Позже | Заказчик сам ставит на второй этап |
| Приложение зрителя: вертикальная лента клипов, поиск по спортсмену и турниру | Входит, параллельная команда | С нашей стороны — API и клипы |
| Автонарезка по таймкодам с наложением данных | Входит | Серверная часть у нас, показ — в приложениях |
| Приложение-пульт с NDI-камерами | Входит как сторонняя параллельная задача | По образцу Mevo, с плагинами (апскейлинг и другие — определить с заказчиком) |
| Подписки зрителей | Возможный отдельный этап | Оплата через ЮKassa, состав подписки — с заказчиком |
