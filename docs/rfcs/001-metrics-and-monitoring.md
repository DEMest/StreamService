# RFC: Внедрение системы мониторинга и сбора метрик

## Проблема
Система находится на этапе активного развития и изменения архитектуры, из-за чего могут быть сбои. При этом о сбоях мы узнаем от пользователей, что ухудшает опыт использования

Также планируется развернуть CDN, однако непонятно, где именно находятся пользователи и сколько ресурсов необходимо

## Задачи
1. Обеспечить наблюдение за системой
2. Сделать уведомление о сбоях
3. Составить набор метрик для формирования требований к CDN

## Текущее состояние
### Технологии и архитектура
То, что сейчас написано, - монолит на NestJs. Он сам и обвязка(MediaMTX, БД, веб-морда на NextJs и т.д.) разведены по разным контейнерам с помощью docker-compose. В качестве http-сервера используется nginx. Всё крутиться на одной машине

### Обратная связь и инциденты
Есть система жалоб от пользователей. С обращением прикрепляется URL, стрим, user-agent. После отправки жалоба попадает в админку и далее на почту

Есть админка, где можно посмотреть загруженность канала и потолок по зрителям. Умеет создавать инциденты и информировать через почту и Telegram

Есть Telegram-бот для создания issues в рабочей группе

### Ограниченность
Мы можем осматривать только ёмкость и QoE. Отсутствуют трекинг ошибок с группировкой и стек-трейсами, метрики по отдельным контейнерам и хосту в целом, централизованные логи

## Метрики
Здесь описаны потенциально полезные метрики для отслеживания системы и прогнозирования нагрузки. Не все из них необходимы к немедленному внедрению, но список полезен для будущего развития, если нам понадобится больше контроля

### Общие подходы
В сфере DevOps есть две базовые методологии для обеспечения наблюдаемости. Для наблюдения за приложениями и отдельными контейнерами используется **RED**. Она состоит из:
- **Rate(интенсивность)** - количество запросов в секунду
- **Errors(ошибки)** - количество необработанных или неуспешных запросов
- **Duration(длительность)** - время на обработку запросов

Для наблюдения за железом и другими ресурсами используется **USE**:
- **Utilization(использование)** - доля времени, когда ресурс был занят выполнением работы
- **Saturation(насыщенность)** - очередь невыполненной работы
- **Errors(ошибки)** - количество ошибочных событий

### Мониторинг железа
- **Процессор**
    - **Total CPU Utilization (%)** - суммарная загрузка процессора по всем типам состояний. Полезна для отслеживания общей утилизации вычислительных мощностей
    - **CPU Load Average (1m, 5m, 15m)** - количество потоков, находящихся в состоянии выполнения или ожидающих своей очереди. Оценивается строго в соотношении с количеством ядер CPU
    - **CPU Wait IO (%)** - процент времени, в течение которого процессор простаивал в ожидании завершения операций ввода-вывода (сигнализирует о дисковой или сетевой недоступности)
- **Память**
    - **Memory Available (%)** - объем памяти, доступный для немедленного выделения процессам (с учетом возможности очистки кэшей). Основной триггер для алертинга
    - **Memory Used / Free / Cached** - утилизация оперативной памяти. Используется для детального анализа распределения ресурсов ОС (приложения vs дисковый кэш)
    - **SWAP Usage (%)** - интенсивность использования пространства подкачки. Рост метрики указывает на жесткую нехватку физической памяти
- **Диск**
    - **Disk Space Used (%)** и **Inodes Used (%)** - процент заполнения объема диска и процент утилизации системных дескрипторов (индексов) файлов
    - **Disk IOPS** и **Throughput (Bps)** - количество операций ввода-вывода в секунду и скорость чтения/записи данных.
    - **Disk Latency (ms)** и **Queue Length** - время отклика диска на операции и длина очереди запросов. Ключевые метрики для определения деградации дисков (особенно SSD/NVMe).
- **Сеть**
    - **Network Traffic / Throughput (Bytes In/Out)** - объем входящего и исходящего трафика в секунду. Применяется для поиска аномалий, DDoS-атак и контроля утилизации сетевого канала.
    - **Dropped Packets / Errors (In/Out)** - количество потерянных или ошибочных пакетов. Свидетельствует о проблемах физического уровня, переполнении буферов ядра ОС или сетевом throttling со стороны облака.

Из перечисленного обязательно стоит взять:
- Total CPU Utilization (%)
- CPU Load Average (1m, 5m, 15m)
- Memory Available (%)
- Disk Space Used (%)
- Network Traffic / Throughput (Bytes In/Out)

Они обеспечивают базовую наблюдаемость системы и позволят реагировать на аномалии

### Мониторинг контейнеров
Контейнеры ограничены механизмами ядра Linux (`cgroups`), поэтому их метрики замеряются относительно выделенных им лимитов (`limits/requests`), а не всего сервера
- **Процессор**
	- **Container CPU Throttling (Throttled Time)** - время, в течение которого ядро ОС искусственно ограничивало CPU контейнера, так как он превысил `cpu limit` 
	- **Container CPU Usage (Relative to Limit)** - процент использования CPU от выделенного лимита. Помогает правильно подобрать ограничения
- **Память**
	- **Container Memory Usage (RSS / Cache)** - память, реально занятая процессами (Resident Set Size), и кэш. Используется для мониторинга утечек памяти
	- **OOMKilled (Out of Memory Killed)** - счетчик принудительных завершений контейнера ядром ОС при превышении `memory limit`. Показывает, что достаточно ли контейнеру памяти
	- **Container Memory Fail Counter** - количество раз, когда контейнер пытался запросить память сверх лимита. Раннее предупреждение до того, как сработает OOMKiller
- **Сеть и диск**
	- **Container Network Rx/Tx** - сетевой трафик конкретного микросервиса. Позволяет найти "прожорливый" контейнер, забивающий канал хоста
	- **Container Block I/O (Read/Write Bps)** - нагрузка на диск со стороны контейнера. Позволяет изолировать приложения, которые слишком активно пишут логи или кэш на диск хоста

Базово стоит внедрить:
- Container CPU Throttling (Throttled Time)
- Container CPU Usage (Relative to Limit)
- Container Memory Usage (RSS / Cache)
- OOMKilled (Out of Memory Killed)

> [!warning] По поводу лимитов у контейнеров
> Стоит отметить, что в текущей конфигурации docker-compose у контейнеров нет лимитов. Это не только потенциально может привести к внезапному падению системы(например, слишком много ингестов потребуют больше памяти и MediaMTX заберёт все ресурсы), но и делает большую часть метрик бессмысленными
