# Приложение и сайт: вход, главный экран, аккаунты, люди, каналы и роли

Дата: 7 ноября 2026. Статус: черновик, формулировки уточняются с заказчиком.
Первый из серии документов, которые по частям детализируют
[`../srs.md`](../srs.md). Здесь — вход, главный экран, личная страница,
раздел «Люди», подписки, имена в чате и модель аккаунтов, каналов, ролей и
регистрации на турнир. Нагрузка, разделение на сервисы, серверы и метрики
описаны в SRS и здесь не затрагиваются.

Всё описанное есть и на сайте, и в приложении; порядок работ — сначала веб,
затем приложение ([`../development-principles.md`](../development-principles.md)).
Только в приложении — сплеш (§2.1) и режим «нет сети».

Коды требований продолжают нумерацию SRS: FR-100 и дальше, NFR-60 и дальше.
Всё в этом документе — в объёме ближайшей разработки.

## 1. Термины

| Термин | Значение |
|---|---|
| Аккаунт | Учётная запись человека в приложении и на сайте: e-mail, пароль, имя, аватар. Один аккаунт — один человек |
| Организатор | Аккаунт, владеющий хотя бы одной организацией. Только ему показывается «Студия» |
| Зритель | Аккаунт без организации. Зритель становится организатором, не заводя новый аккаунт |
| Организация | Арендатор платформы: федерация, лига, клуб, школа. Владеет каналами, турнирами и настройками чата |
| Канал | Единица трансляции: свой ключ ингеста, приватность, запись и архив. В коде и API — `Stream`. У каждого канала есть **категория** |
| Безликий канал | Канал категории `personal`: есть у каждого аккаунта, не показывается в каталоге и поиске каналов. Носитель идентичности человека в чате, подписках и ролях |
| Личная страница | Публичная страница аккаунта: имя, аватар, роли, подписки. Её владелец здесь же меняет свои данные и настройки |
| Люди | Раздел сайта и приложения со списком зарегистрированных аккаунтов и переходом на их личные страницы |
| Подписка | Отметка «следить за»: организацией, человеком или каналом. Источник уведомлений и персональной ленты |
| Роль | Дополнительное качество аккаунта: «Школа», «Участник соревнований». У роли есть набор атрибутов, который расширяется без миграции схемы |
| Турнир | Событие внутри сервиса (FR-30): название, дата, площадки; к нему привязаны каналы, эфиры, записи, клипы и регистрации участников |
| Регистрация на турнир | Запись «участник X заявлен на турнир Y тем-то». Создаётся организатором турнира или школой участника |
| Студия | Раздел главного экрана организатора: кабинет организации (FR-20–FR-24) |

## 2. Сценарии

### 2.1 Сплеш, вход и регистрация

```
запуск приложения
      │
      ▼
   СПЛЕШ ── есть сохранённая сессия? ──нет──► ВХОД ◄──► РЕГИСТРАЦИЯ
      │                                         │
     да                                         │ успех
      │ сессия действительна                    │
      ▼                                         ▼
 ГЛАВНЫЙ ЭКРАН ◄────────────────────────────────┘
      │
      └── Личная страница → «Выйти» / «Сменить аккаунт» ──► ВХОД
```

1. Сплеш один для всех — на нём нет выбора «я зритель / я организатор».
   Приложение молча проверяет сохранённую сессию (`GET /v1/auth/me`, при
   просроченном access — `POST /v1/auth/refresh`). На сайте вместо сплеша —
   страница входа `/login`, на которую ведут закрытые разделы.
2. Сессия действительна → главный экран, без единого нажатия. Сессии нет
   или она отозвана → экран входа.
3. API недоступен, а сессия сохранена → главный экран в режиме «нет сети»
   с кнопкой повтора; выход и смена аккаунта доступны и оттуда. Приложение
   не упирается в сплеш из-за сервера.
4. Выйти и войти другим аккаунтом, в том числе зарегистрировать новый, можно
   всегда — с личной страницы. Выход отзывает refresh-токен на сервере и
   стирает сессию на устройстве.
5. Регистрация: e-mail, пароль, имя и **обязательная отметка согласия** с
   политикой конфиденциальности и пользовательским соглашением, со ссылками
   на оба документа. Без отметки аккаунт не создаётся. Сервер сохраняет
   момент согласия и редакцию политики — ту же, что показывает сайт
   (`LEGAL.version` в `apps/web/src/lib/legal.ts`, FR-82). E-mail
   подтверждается письмом.
6. Когда выходит новая редакция политики, при следующем входе человек видит
   её и заново даёт согласие; пока не согласился, дальше экрана согласия не
   проходит, но может выйти из аккаунта.
7. Вход — по e-mail и паролю. Двухфакторная аутентификация в этот этап не
   входит; позже она появится как настройка на личной странице. Телефон и
   вход через сторонние сервисы — открытый вопрос (§7).

### 2.2 Главный экран и навигация

**Главное для зрителя — последние схватки.** Приложение открывается лентой
свежих клипов схваток
([`2026-11-07-tournament-page.md`](2026-11-07-tournament-page.md)). Сверху,
над лентой, — текущий турнир или, если такого нет, ближайший предстоящий:
обложка, название, время, переход на страницу турнира. Текущий турнир с
трансляцией помечен «эфир», без трансляции — «идёт турнир» с числом новых
схваток.

```
 ┌──────────────────────────┐
 │ ТУРНИР СЕЙЧАС / СКОРО    │   текущий или ближайший турнир
 │ Кубок области · ● эфир   │
 ├──────────────────────────┤
 │ (●)(●)(●)(●)(●) →        │   подписки: каналы, люди, организации
 ├──────────────────────────┤
 │ ┌──────┐ Иванов — Петров │   последние схватки, свои подписки выше
 │ │превью│ Кубок · ковёр 2 │
 │ └──────┘ ♥ 12  💬 3      │
 │ ┌──────┐ Сидоров — Козлов│
 │ │превью│ …               │
 │ └──────┘                 │
 │ …                        │
 ├──────────────────────────┤
 │ Главная Архив Люди Я  [С]│   нижняя панель; «Студия» — у организатора
 └──────────────────────────┘
```

- **Подписки в приоритете.** Под турниром — строка каналов, людей и
  организаций, на которые человек подписан, для быстрого перехода; те, где
  сейчас эфир, — первыми. В ленте схватки с этих каналов и турниров стоят
  выше остальных.
- **Навигация вертикальная.** Все экраны листаются вниз: лента, архив,
  люди, личная страница, «Студия». Разделы переключаются нижней панелью.

| Раздел | Зритель | Организатор | Что внутри |
|---|---|---|---|
| Главная | да | да | Текущий или ближайший турнир, строка подписок, лента последних схваток |
| Архив | да | да | Записи трансляций, клипы, оконченные турниры; поиск по названию и человеку, фильтры ([`2026-11-07-tournament-page.md`](2026-11-07-tournament-page.md), §3.8) |
| Люди | да | да | Зарегистрированные аккаунты, поиск по имени, переход на личную страницу (§2.4) |
| Личная страница | да | да | Свой профиль: аватар, имя, роли, подписки, баланс медиагента, настройки, выход и смена аккаунта (§2.3) |
| **Студия** | нет | **да** | Кабинет организации: каналы и их настройки (FR-20, FR-21), живая статистика эфира (FR-22), записи и место в архиве (FR-23), пульт и турниры (FR-24, FR-30), настройки организации и чата |

Поиск — строкой вверху «Главной» и «Архива», а не отдельным разделом.
На сайте те же разделы — пункты шапки, главная страница сайта тоже
открывается турниром и лентой схваток.

**Где горизонталь напрашивается уже сейчас.** Это исключения из
вертикальной навигации; позже их станет больше.

| Место | Что горизонтально | Почему |
|---|---|---|
| Плеер эфира и клипа | Поворот телефона — плеер на весь экран | Видео горизонтальное; так смотрят на YouTube |
| Строка подписок на «Главной» | Аватары листаются вбок | Быстрый переход к своим каналам, не отнимая высоту у ленты |
| Фильтры архива и ленты схваток турнира | Чипы фильтров листаются вбок | Фильтров много, а строка одна |
| Выбор камеры в плеере | Кнопки камер 1–4 в ряд | Переключение одним касанием, не уходя из плеера |

«Студия» появляется в момент, когда аккаунт становится организатором, и
исчезает, когда перестаёт им быть; перезапуск приложения не нужен — права
приходят из `/v1/auth/me`. Разделы вне «Студии» одинаковы для всех:
организатор смотрит чужие эфиры как зритель.

### 2.3 Личная страница

- У каждого аккаунта одна личная страница. Её видят все, а владелец на ней
  же редактирует своё.
- Что на странице: аватар, имя, роли с их публичными атрибутами (§2.7),
  организации, которыми человек владеет, подписки, клипы участника.
- Что владелец меняет: аватар (загрузка, обрезка до квадрата, удаление),
  имя, роли, подписки, пароль и e-mail (с подтверждением письмом).
  Аватар хранится в S3 так же, как картинка организации, и сжимается на
  сервере; без аватара показываются инициалы.
- Настройки здесь же: уведомления по подпискам и, после этого этапа,
  двухфакторная аутентификация.
- E-mail и контакты никогда не показываются другим людям.

### 2.4 Люди

- Раздел со списком зарегистрированных аккаунтов: аватар, имя, роли.
  Поиск по имени и фильтр по роли («Школа», «Участник»).
- Карточка ведёт на личную страницу, с неё можно подписаться на человека.
- Личные страницы не индексируются поисковиками и не попадают в sitemap:
  это страницы людей, а не трансляций, и правило индексации (FR-81) их не
  пускает.
- Может ли человек скрыть себя из раздела — открытый вопрос (§7).

### 2.5 Подписки

- Подписаться можно на **организацию**, **человека** или **канал** — с их
  страниц, из раздела «Люди» и из плеера.
- Подписки видны на личной странице; там же от любой можно отписаться.
- Подписка определяет уведомления: на организацию и канал — «эфир начался»
  (FR-43); на человека — его новые клипы и эфиры каналов, связанных с его
  ролями. Какие уведомления присылать, человек настраивает на личной
  странице.
- Подписки формируют «Главную»: строка подписок для быстрого перехода и
  порядок ленты схваток — сначала то, на что человек подписан (§2.2). Так
  же сортируется архив.

### 2.6 Имена в чате

- Авторизованный человек пишет в чат трансляции под именем и аватаром своего
  аккаунта; отдельного никнейма у него нет.
- Нажатие на имя в чате открывает личную страницу автора.
- Имя в чате всегда текущее: смена имени на личной странице видна во всех
  чатах.
- Гость на сайте может писать в чат под никнеймом, сохранённым в браузере
  (FR-14); его сообщения помечены как гостевые, чтобы гость не выдавал себя
  за зарегистрированного человека. Нужно ли гостям писать в чат вообще —
  открытый вопрос (§7).

### 2.7 Роли «Школа» и «Участник соревнований»

- Роль запрашивается с личной страницы любым аккаунтом, зрителем или
  организатором. У аккаунта может быть несколько ролей; одна и та же роль
  дважды не выдаётся.
- Роль — сущность с **расширяемым набором атрибутов**: у «Школы» —
  название, город, тренер, контакт; у «Участника» — фамилия, имя, год
  рождения, весовая категория, школа. Набор не окончательный: атрибуты
  хранятся как документ, а в колонки схемы выносится только то, по чему
  нужен поиск (фамилия участника — для FR-33).
- На личной странице и в разделе «Люди» показываются только публичные
  атрибуты: у школы — название и город, у участника — фамилия, имя, школа.
  Год рождения, весовая категория и контакты видны организатору турнира и
  школе участника, но не всем.
- Кто подтверждает роль — сам аккаунт, организатор или суперадмин —
  открытый вопрос (§7). До решения роль действует с момента создания.
- Роль может иметь свой канал соответствующей категории: у школы — страница
  школы с её эфирами и участниками, у участника — его клипы со всех
  турниров (результат автонарезки FR-32 раскладывается по участникам).

### 2.8 Каналы

- При создании аккаунта создаётся его **безликий канал** (`personal`). Он не
  показывается в каталоге и поиске каналов; именно он хранит роли и
  связывает человека с его чатом и подписками.
- Организатор заводит в «Студии» сколько угодно каналов категории
  `organizer`; они показываются на странице организации, в каталоге, поиске
  и sitemap по правилам FR-16 и FR-81.
- Каналы категорий `school`, `participant` и `tournament` появляются вместе
  с ролью или турниром (§2.7, §2.9). Видимость канала определяется его
  категорией в одном месте на бэкенде, рядом с правилом индексации (NFR-45).
- Что человек может делать со своим безликим каналом сверх чата и подписок
  (например, вести эфир с телефона, FR-50) — открытый вопрос (§7).

### 2.9 Турнир и регистрация участников

- Турнир создаёт организатор в «Студии» (FR-24, FR-30). К турниру
  привязываются каналы категории `tournament` — те же Stream'ы с тем же
  ингестом, с категорией и ссылкой на турнир.
- Участника на турнир регистрирует **организатор турнира** или **школа**,
  к которой участник привязан. Сам участник заявку не подаёт — осознанное
  упрощение, чтобы не проектировать модерацию до того, как станет понятен
  реальный процесс.
- Регистрация хранит: турнир, участника, кто зарегистрировал, когда, статус.
  Статусы на старте — `registered` и `withdrawn`; подтверждение и
  отклонение добавляются, когда станет понятен реальный процесс.
- Список зарегистрированных участников — вход для секретаря (FR-31) и для
  подписи клипов (FR-32): фамилия на клипе берётся из регистрации, а не
  вводится руками второй раз.

## 3. Требования

### 3.1 Аккаунт и вход

| Код | Требование |
|---|---|
| FR-100 | Регистрация аккаунта по e-mail, паролю и имени с подтверждением e-mail письмом; вход по e-mail и паролю; восстановление пароля письмом |
| FR-101 | Один аккаунт работает и в приложении, и на сайте. В приложении аккаунт обязателен; просмотр на сайте остаётся без аккаунта (FR-10, FR-60) |
| FR-102 | Сплеш приложения один для всех: при действительной сессии приложение само открывает главный экран; без сессии — экран входа. Выбора «кто я» на сплеше нет |
| FR-103 | Выйти и войти другим аккаунтом (или зарегистрировать новый) можно с личной страницы в любой момент; выход отзывает refresh-токен |
| FR-104 | При недоступном API с сохранённой сессией приложение открывает главный экран в режиме «нет сети», не задерживаясь на сплеше |
| FR-105 | Организация принадлежит аккаунту-владельцу. Организации, заведённые до появления аккаунтов, получают владельца при миграции с тем же логином и паролем (§5) |
| FR-106 | Аккаунт становится организатором, когда ему передаётся или для него создаётся организация. Кто это делает — суперадмин по заявке (FR-70) или сам аккаунт — открытый вопрос; до решения — суперадмин |
| FR-107 | Регистрация невозможна без отметки согласия с политикой конфиденциальности и пользовательским соглашением; сервер хранит момент согласия и редакцию политики (FR-82). При новой редакции согласие запрашивается заново при следующем входе |
| FR-108 | Двухфакторная аутентификация в этап не входит; место для неё — настройки личной страницы |

### 3.2 Главный экран

| Код | Требование |
|---|---|
| FR-110 | Нижняя панель: Главная, Архив, Люди, Личная страница — у всех; **Студия** — только у организатора. На сайте — те же разделы в шапке |
| FR-114 | «Главная» зрителя — лента последних клипов схваток; над ней текущий турнир, а если его нет — ближайший предстоящий |

## 5. Модель данных и миграция

Схема в продакшне — `prisma/schema.prisma`: `User` (суперадмин, рекламный
менеджер), `Organization` с собственным `passwordHash`, `Stream`,
`Broadcast`, `Recording`, `ChatMessage`. Всё ниже добавляется поверх неё;
ни одна существующая таблица не переименовывается.

```
Account ──владеет──► Organization ──► Stream (category) ──► Broadcast ──► Recording
   │  │                    │                 ▲
   │  │                    └── Event ────────┘  (category = tournament)
   │  │                          │
   │  │                          └── Registration ──► AccountRole (participant)
   │  │
   │  └── Subscription ──► Organization | Account | Stream
   │
   └── AccountRole (school | participant) ──► Stream (category = school | participant,
                                                      orgId = personal-организация аккаунта)
```

Каждый Stream принадлежит Organization: канал школы или участника лежит под
скрытой `personal`-организацией того же аккаунта, а не вне тенантности.

| Таблица | Содержание | Зачем так |
|---|---|---|
| `Account` | **Новая**: `id`, `email` (unique), `passwordHash`, `displayName`, `avatarPath` (nullable, S3-ключ `images/account/<id>.jpg`), `emailVerifiedAt`, `consentAt`, `consentVersion`, `createdAt` | Аккаунт человека. Отдельно от `User`: там служебные роли платформы с другим жизненным циклом и другим поддоменом входа. Поля согласия — те же, что у `ContactRequest` и `Feedback` |
| `Organization` | `+ownerAccountId` (nullable на время миграции), `+kind` = `organizer` \| `personal` | Владение и «организаторство». `personal` — скрытый арендатор человека: безликий канал живёт в той же модели `Organization → Stream`, и `/v1/org/*`, пути ингеста `live/<slug>/<stream>`, запись, чат и приватность работают без второй ветки кода. `slug` и `name` у неё генерируются (`u-<id аккаунта>`), не выбираются человеком и не пересекаются ни с публичными слагами, ни с `RESERVED_STREAM_SLUGS`. Вместе с ней создаётся её единственный Stream `personal`; организация `organizer` создаётся без Stream'ов |
| `Organization.passwordHash` | Остаётся, пока есть организации без `ownerAccountId`; `AuthService.login` пробует `Account`, затем `Organization` по slug | Ни одна организация не теряет вход в день выкатки |
| `Stream` | `+category` = `organizer` \| `personal` \| `school` \| `participant` \| `tournament` (default `organizer`), `+eventId` (nullable) | Категории каналов. Бэкфилл: все существующие строки — `organizer` |
| `Subscription` | **Новая**: `id`, `accountId`, `targetType` (`organization` \| `account` \| `stream`), `targetId`, `notify Json`, `createdAt`; `@@unique([accountId, targetType, targetId])`, индекс по `(targetType, targetId)` | Одна таблица на три вида подписок; индекс по цели — чтобы при старте эфира быстро найти, кого уведомить |
| `AccountRole` | **Новая**: `id`, `accountId`, `kind` (`school` \| `participant`), `attributes Json`, `searchName` (nullable, индекс), `schoolRoleId` (nullable, self-relation для участника), `streamId` (nullable), `createdAt`; `@@unique([accountId, kind])` | Роль с расширяемыми атрибутами; какие из них публичны — правило FR-135 в коде, а не флаг в данных |
| `ParticipantConsent` | **Новая**: `id`, `participantRoleId`, `scope` (`publish` \| `filming`), `givenByAccountId`, `giver` (`self` \| `guardian`), `consentAt`, `consentVersion`, `revokedAt` (nullable) | Согласия участника: публикация страницы несовершеннолетнего (FR-136) и съёмка схваток ([`2026-11-07-media-agent-app.md`](2026-11-07-media-agent-app.md), FR-224, FR-225) — одна таблица |
| `Event` | **Новая**, из FR-30: `id`, `orgId`, `title`, `startsAt`, `endsAt`, `venueCount`, `createdAt` | Турнир. В истории миграций есть `20260702000000_drop_event`, удалившая прежние `Event` и `EventStream` (M:N); здесь связь другая — `Stream.eventId` 1:N; старую миграцию не трогать, только новая вперёд |
| `Registration` | **Новая**: `id`, `eventId`, `participantRoleId`, `registeredByAccountId`, `status`, `createdAt`; `@@unique([eventId, participantRoleId])` | Заявка участника на турнир |
| `ChatMessage` | `+accountId` (nullable) | Сообщение авторизованного человека привязано к аккаунту; имя и аватар берутся из `Account` при выдаче, поэтому всегда текущие. Гость — по никнейму |
| JWT | `role: 'account'` с `accountId` и списком `orgIds` владения; `org_admin` остаётся для организаций без владельца | Клиент решает про «Студию» по `organizations[]` в `/v1/auth/me` |

Порядок миграции (шаги 1 и 3 — схемные миграции в `prisma/migrations/`,
шаг 2 — идемпотентный скрипт в `prisma/data/004-*.ts`, как остальные
бэкфиллы проекта; каждый шаг обратим):

1. Таблицы `Account`, `Subscription`, `AccountRole`, `ParticipantConsent`, `Event`, `Registration`;
   колонки `Organization.ownerAccountId`, `Organization.kind`,
   `Stream.category`, `Stream.eventId`, `ChatMessage.accountId` — все
   nullable или с default.
2. Бэкфилл: на каждую `Organization` — `Account` с `email = <slug>@legacy.local`
   (или настоящий e-mail, если организация его сообщила), `passwordHash`
   копируется, `ownerAccountId` проставляется, `kind = organizer`; все
   `Stream` — `category = organizer`. У таких аккаунтов `consentAt` пуст —
   согласие запрашивается при первом входе (FR-107).
3. Вход через `Account`; `Organization.passwordHash` помечается устаревшим и
   удаляется отдельной миграцией, когда организаций без владельца не
   останется.

При реализации вместе с кодом обновляется `CLAUDE.md`: хранение никнейма
чата, роли JWT и таблица разделов `apps/web/src/lib/sections.ts`, правило
создания Stream'ов у `personal`-организации, новые публичные маршруты.

## 6. Интерфейсы API (эскиз)

| Маршрут | Назначение | Кто |
|---|---|---|
| `POST /v1/auth/register`, `POST /v1/auth/verify-email`, `POST /v1/auth/forgot-password` | Регистрация (с версией согласия) и восстановление | без авторизации |
| `POST /v1/auth/consent` | Согласие с новой редакцией политики | аккаунт |
| `POST /v1/auth/login`, `/refresh`, `/logout`, `GET /v1/auth/me` | Сессия; `me` отдаёт `organizations[]`, `roles[]` и признак «нужно согласие» | cookie или Bearer |
| `GET/PATCH /v1/me`, `PUT/DELETE /v1/me/avatar` | Личная страница: имя, e-mail, пароль, аватар, настройки | аккаунт |
| `GET/POST/DELETE /v1/me/roles` | Роли аккаунта | аккаунт |
| `GET/POST/DELETE /v1/me/subscriptions` | Подписки на организации, людей и каналы | аккаунт |
| `GET /v1/public/people`, `GET /v1/public/people/:id` | Раздел «Люди» и публичная карточка личной страницы | без авторизации |
| `/v1/org/*` | Кабинет организации; организация берётся из токена, при нескольких — из заголовка или пути | владелец организации |
| `GET/POST /v1/org/events`, `GET/POST/DELETE /v1/org/events/:id/registrations` | Турниры и регистрации организатора | владелец организации |
| `GET/POST/DELETE /v1/me/roles/school/registrations` | Регистрации участников школой | аккаунт с ролью «Школа» |
| `GET /v1/public/events/:id` | Страница турнира | без авторизации |
| WebSocket `/chat` | `join` принимает сессию аккаунта; сообщения несут `accountId`, имя и аватар | аккаунт или гость |

Маршруты — смысловой набор. Сайту их отдаёт `web-api`, приложению —
`mobile-api` со своим версионированным контрактом (SRS NFR-46). Оба
работают с одной базой и одними правилами через общий пакет (NFR-47): в
частности, видимость каналов и личных страниц и состав публичной карточки
(FR-122, FR-161, NFR-64) решаются в нём, а не в каждом бэкенде.
