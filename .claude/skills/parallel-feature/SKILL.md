Ты — оркестратор параллельной разработки в этом репозитории (StreamService:
NestJS + Next.js + Prisma + MediaMTX, живой прод на liga-live.ru). Тебе
передан текст в аргументе команды — это может быть явный список фич через
`;` или перевод строки, а может быть произвольное описание одной или
нескольких задач одним куском текста. Если аргумент пустой — спроси
пользователя, какую задачу разобрать, и дождись ответа, не продолжай с
пустым входом.

Работай в главном checkout'е (не во вложенном worktree). Проверь `git
status` — рабочая копия должна быть чистой. Если грязная — останови и
попроси разобраться руками, не трогай чужие незакоммиченные изменения.

**Важно про этот репозиторий:** `/home/rootuser/StreamService` — это не
только исходники, это рабочий каталог живого прода. Ни ты, ни фоновые
сессии не запускают здесь `docker compose up/down/restart` — проверка идёт
сборкой и тестами. Выкатку делает автодеплой после мержа.

## Шаг 1 — Разбор задачи
Прочитай входной текст и сам реши, на какие независимые фичи он бьётся —
если фичи уже разделены явно (через `;`, перевод строки или просто по
смыслу), уважай эти границы; если это одно связное описание одной задачи —
это одна фича. Если две фичи явно затрагивают один и тот же файл — предупреди
пользователя и предложи объединить их в одну последовательную задачу вместо
параллельной: одновременная работа над одним файлом в разных worktree всё
равно даст конфликт на шаге слияния, только позже и дороже.

Отдельно предупреди, если фичи попадают в места, где источник истины
дублирован (`layout-presets.ts` в apps/api и apps/web) или где правка
неизбежно затронет и схему Prisma, и оба приложения — такие задачи лучше
вести одной сессией.

## Шаг 2 — Запуск параллельных фоновых сессий
Для каждой независимой фичи придумай короткий kebab-case слаг (например
`chat-slowmode`, `dashboard-storage-card`) и оцени её сложность своими
словами — мелкая точечная правка (текст, стиль, один параметр) заметно
проще, чем новая ручка API с миграцией Prisma или правки в конвейере
HLS/записи, а многофайловая или архитектурная работа — сложнее их обеих. По
этой оценке сам выбери модель (`--model`: `haiku`/`sonnet`/`opus` — алиасы
последних версий) и уровень усилий (`--effort`:
`low`/`medium`/`high`/`xhigh`/`max`) под конкретную фичу, без фиксированной
таблицы правил — решай по ситуации.

Проверь, залогинен ли у тебя сырой `claude` CLI — командой `claude auth
status` (не запускай `claude --bg` просто для проверки, это не безобидная
проверка, а реальный запуск фоновой сессии). Если залогинен (обычно так у
живого `claude` в чьём-то терминале) — запусти отдельную фоновую сессию с
явным `--worktree`, иначе она НЕ получит свой git worktree и будет
работать в общей рабочей копии, мешая остальным фоновым сессиям:

    claude --bg --worktree <slug> --name <slug> --model <модель> --effort <уровень> "Реализуй: <точный текст фичи>. Работай по
    правилам CLAUDE.md этого проекта: архитектура и Product Constraints,
    git-флоу (ветка -> PR -> зелёный CI -> merge, никогда не пушить в main
    напрямую), обязательная самопроверка через task-completion-validator,
    qa-browser-tester (если менялся apps/web), claude-md-compliance,
    code-quality-pragmatist и live-safety-auditor. Не запускай docker
    compose — это каталог живого прода. Когда всё проходит — закоммить без
    подписи и открой PR через gh pr create. Сам PR не мерджи — это сделает
    оркестратор; это правило переопределяет автономный мердж по умолчанию
    из CLAUDE.md для этой конкретной фоновой сессии."

Если `claude` CLI не залогинен (обычно так в харнесс-сессиях вроде Claude
Desktop) — используй свой родной Agent-инструмент вместо этого:
`run_in_background: true, isolation: "worktree"`, с тем же полным текстом
задачи в prompt (включая оговорку про то, что сам PR мерджить не нужно —
без неё фоновый агент может откатиться на автономный мердж по умолчанию
из CLAUDE.md и смёрджить свой PR сам) и с моделью, выбранной по той же
оценке сложности (параметра уровня усилий там нет).

Запусти это для каждой фичи по очереди — каждый вызов сразу возвращает
управление, фоновая сессия работает независимо от остальных. Сохрани
список слагов — они понадобятся дальше.

## Шаг 3 — Мониторинг
Если ты использовал сырой CLI: сообщи пользователю, что можно в любой
момент открыть `claude agents` в отдельном терминале и увидеть статус всех
фоновых сессий (Working / Needs input / Completed / Failed) в одном
экране. Периодически проверяй прогресс сам: `claude agents --json` (или
`--all --json` вместе с уже завершёнными) даёт список сессий
машиночитаемо — удобно опрашивать в цикле, не дожидаясь, пока пользователь
откроет терминал сам.

Если ты использовал свой Agent-инструмент: `claude agents` эти сессии не
покажет (это разные механизмы) — отслеживай их напрямую через результаты
своих вызовов: синхронный вызов сразу возвращает результат, фоновый
(`run_in_background: true`) — придёт уведомление о завершении, ждать его
специально не нужно.

В обоих случаях дополнительно смотри `gh pr list` — появились ли PR от
каждой ветки.

Не считай фичу готовой к слиянию, пока не выполнено всё:
- фоновая сессия завершилась (Completed, не Failed);
- по ветке открыт PR;
- CI по этому PR зелёный;
- `live-safety-auditor` по этому PR не вернул FAIL.

Если какая-то сессия зависла в Needs input или Failed — сообщи об этом
пользователю с конкретикой, не додумывай ответ за него и не пытайся сам
разрулить то, что явно требует решения человека.

## Шаг 4 — Последовательное слияние и конфликты
Когда фичи готовы, сливай их в main ОДНУ ЗА ДРУГОЙ — в порядке готовности
(или в порядке, который явно укажет пользователь). **Помни: каждый мерж
запускает автодеплой на живой прод**, поэтому между мержами убеждайся, что
предыдущая выкатка прошла (Actions → job `deploy` зелёный), и только потом
мерджи следующий PR. Два мержа подряд дадут две выкатки внахлёст.

Для каждого PR по очереди:

1. `gh pr checks <номер> --watch` — дождись зелёного CI. Если красный —
   остановись и сообщи, не мерджи сломанное.
2. Вызови `live-safety-auditor` на diff этого PR. Если он вернул FAIL
   (изменение требует рестарта mediamtx или несёт блокирующую миграцию) —
   НЕ мерджи: сообщи пользователю, что этот PR нужно выкатывать в простое
   эфира, и переходи к следующему.
3. `gh pr merge <номер> --squash --delete-branch` — попробуй смерджить.
4. Если merge не прошёл из-за конфликта:
   - `gh pr checkout <номер>` — переключись на ветку этого PR.
   - `git fetch origin && git merge origin/main` — подтяни обновлённый main
     (в нём уже сидит предыдущая слитая фича).
   - Разреши конфликты сам: прочитай оба варианта в конфликтующих местах и
     сохрани оба намерения там, где это возможно, не выбрасывай
     функциональность одной из фич без явной причины. Если конфликт
     семантический, а не текстовый (обе фичи по-разному меняют одну и ту же
     логику) и правильное решение неочевидно — остановись и спроси
     пользователя, а не гадай.
   - Отдельно проверь конфликты в `prisma/migrations/`: две фичи могли
     добавить миграции с пересекающимся смыслом. Их нельзя "слить" текстом —
     разберись, применимы ли обе подряд.
   - Прогони самопроверку заново (task-completion-validator,
     qa-browser-tester, claude-md-compliance) на смёрженном результате — это
     не опционально: по отдельности рабочие фичи вместе могут сломать
     что-то на стыке.
   - Закоммить (без подписи), запушить ветку PR, повторить `gh pr merge`.
5. После успешного слияния дождись зелёного `deploy` в Actions, потом
   переходи к следующему PR.

## Шаг 5 — Итог
Когда все фичи смёрждены, напиши пользователю короткий отчёт: какие фичи
слиты и в каком порядке, были ли конфликты и как они разрешены, ссылки на
смёрженные PR, и прошли ли выкатки. Если что-то остановилось на середине
(сессия зависла, тесты не проходят, конфликт нельзя разрешить безопасно,
live-safety-auditor заблокировал выкатку) — опиши, на каком именно шаге и
что нужно от пользователя, а не пытайся любой ценой довести дело до конца.
