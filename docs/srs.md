# SRS — спецификация требований к платформе Liga Live

Версия: октябрь 2026. Статус: рабочая, требования не утверждены заказчиком
и подтверждаются на юз-кейсах. Документ дополняет [`vision.md`](vision.md)
(почему продукт такой и куда развивается) и [`requirements-talk.md`](requirements-talk.md)
(выжимка для выступления): здесь — полный перечень требований с номерами
и статусом. Проектные спеки апреля 2026 в [`specs/`](specs/) и
[`superpowers/specs/`](superpowers/specs/) — история решений, этот документ их
заменяет.

Обозначения статуса: **Есть** — реализовано и работает в продакшне;
**План** — в объёме ближайшей разработки; **Возможно** — отдельный этап,
решение не принято. Пометка «если изменится» — запасной вариант для
решения, которое заказчик ещё не подтвердил.

## 1. Введение

### 1.1 Назначение

Документ фиксирует требования к платформе Liga Live (liga-live.ru) и её
клиентам: что система уже делает, что должна делать после ближайшего этапа
разработки и каким ограничениям обязана соответствовать. Адресаты — команда
разработки, кураторы учебного проекта и заказчик.

### 1.2 Область

Платформа трансляций спортивных турниров. Организация (федерация, лига,
клуб) ведёт эфир со своей площадки, зритель смотрит в браузере или в
приложении, запись остаётся в архиве. Стартовая ниша — спортивная борьба;
ни одна сущность системы не привязана к виду спорта.

В объём входят: веб-платформа (сайт, кабинет организации, админка),
серверная часть (приём и раздача видео, архив, API, чат), приложение
зрителя и приложение организатора для iOS и Android, инфраструктура и
процесс разработки. Не входят: собственное производство контента,
AI-комментатор (направление развития из vision §3.3, вне ближайшего этапа),
режиссура на стороне сервера, платёжные операции до отдельного этапа.

### 1.3 Термины

| Термин | Значение |
|---|---|
| Организация | Арендатор платформы: федерация, лига, клуб. Имеет логин, несколько потоков, настройки чата |
| Поток (Stream) | Единица трансляции внутри организации: свой ключ ингеста, приватность, режим подачи и записи. Один входящий поток на Stream |
| Эфир (Broadcast) | Одна сессия потока от первого подключения кодера до последнего отключения |
| Запись (Recording) | Готовая запись эфира в архиве: файл и плейлист в S3-хранилище |
| Событие | Турнир: название, дата, число ковров; объединяет эфиры, записи и клипы |
| Клип | Фрагмент записи с одной схваткой, вырезанный по таймкодам, с наложенными фамилиями и счётом |
| Ковёр | Площадка, на которой идёт схватка; на турнире их несколько, у каждого своя камера |
| Ингест | Приём видео от кодера организации по SRT или RTMP |
| Композит | Один поток, в кадре которого собрано несколько камер (раскладка 2×2); зритель вырезает нужную четверть на устройстве |
| Лесенка качеств | Копии потока в 720p, 480p, 240p, которые сервер делает для доставки; исходный поток не перекодируется |
| NDI | Протокол передачи видео между устройствами в одной локальной сети |
| CDN | Сеть серверов, раздающая видео зрителям ближе к ним и снимающая трафик с сервера платформы |
| Суперадмин | Оператор платформы: заводит организации, следит за ёмкостью, разбирает заявки |

### 1.4 Источники

- `vision.md` — продукт, текущая архитектура, направления развития, раздел 4 с требованиями.
- `requirements-talk.md` и `requirements-talk-slides.pdf` — выжимка и презентация.
- Корневой `CLAUDE.md` и `README.md` — что реализовано и какие правила не нарушаются.
- Пожелания заказчика (переписка, октябрь 2026) и отчёт команды по заданию 1 (идея, аудитория, рынок, интервью).

## 2. Общее описание

### 2.1 Продукт и контекст

Платформа работает в продакшне на одном сервере: приём SRT/RTMP, раздача
HLS, архив в S3-совместимом хранилище, чат, кабинет организации, админка,
автоматическая выкладка обновлений под живым эфиром. Ближайший этап —
функции для организатора турнира, мобильные клиенты, вынос раздачи видео на
CDN и несколько серверов, разделение серверной части на сервисы.

### 2.2 Пользователи

| Пользователь | Как входит | Что делает |
|---|---|---|
| Зритель | Без регистрации | Смотрит эфир и архив, выбирает камеру, пишет в чат, ищет организацию, трансляцию или запись (турнир и спортсмена — после FR-30 и FR-33). В приложении — подписывается на организации и получает уведомления |
| Организация (`org_admin`) | Логин и пароль организации | Ведёт потоки и эфиры, управляет ключами и записью, смотрит статистику, создаёт события |
| Секретарь турнира | Через приложение секретаря, которое уже есть у заказчика | Ведёт протокол схватки: фамилии, счёт, начало и конец. Платформа забирает эти данные |
| Суперадмин (`superadmin`) | Логин и пароль, отдельный поддомен | Организации, заявки, обратная связь, ёмкость сервера, реклама |
| Рекламный менеджер (`ad_manager`) | Логин и пароль, отдельный поддомен | Рекламные объявления платформы |

### 2.3 Платформы

| Платформа | Клиент | Статус |
|---|---|---|
| Веб, браузер на ПК и телефоне | Страница трансляции и архив, кабинет организации, админка | Есть |
| iOS и Android | Приложение зрителя | План, параллельная команда |
| iOS и Android | Приложение организатора | План, параллельная задача |

Все клиенты работают с одним API. Если изменится: отдельный слой API для
мобильных, если контракт веба им не подойдёт.

### 2.4 Инварианты

| Код | Требование | Почему |
|---|---|---|
| INV-1 | Сервер не пересобирает и не разрезает видео. Компоновка — у зрителя: кроп квадранта композита или раскладка нескольких потоков организации на одном экране | Один канал с арены на всю трансляцию; N зрителей — N декодирований тех же потоков; нет серверного транскода основного фида. Это экономика продукта |
| INV-2 | Платформа не привязана к виду спорта | Стартовая ниша — борьба, но ни одна сущность не знает про ковры; рынок расширяется без переделки |

### 2.5 Допущения и зависимости

- Приложение секретаря у заказчика уже есть; глубина интеграции (события в реальном времени или протокол после схватки) определяется после изучения его API.
- Сборка картинки с нескольких камер происходит на площадке: в видеомикшере (vMix, OBS) или в приложении организатора. Сборка картинки на сервере в объём не входит (INV-1); если заказчик вернётся к этому запросу, он оценивается отдельно как изменение объёма работ.
- CDN-провайдер выбирается по цене трафика и точкам присутствия в регионах зрителей (кандидаты: Yandex Cloud CDN, EdgeCenter, Selectel).
- Платные подписки и приём оплаты — после юридической подготовки оферт; провайдер оплаты — ЮKassa (источник — заказчик, переписка октября 2026).
- Цифры целевой нагрузки проверяются нагрузочным тестом; текущий потолок рассчитан, а не измерен.

## 3. Функциональные требования

### 3.1 Приём видео и эфир

| Код | Требование | Статус |
|---|---|---|
| FR-1 | Приём видео по SRT (passphrase) и RTMP (ключ) от любого кодера; ключ ингеста уникален для потока и перевыпускается из кабинета | Есть |
| FR-2 | У организации может быть несколько потоков; каждый поток — один входящий сигнал: композит или один ракурс | Есть |
| FR-3 | Эфир создаётся при подключении кодера и закрывается при отключении; в ручном режиме при включённой записи разрыв сигнала до 60 минут (настраивается, `RECORDING_GLUE_TIMEOUT_MINUTES`) склеивается в один эфир; по истечении окна эфир закрывается моментом обрыва, а не моментом проверки | Есть |
| FR-4 | Сервер делает лесенку качеств (720p, 480p, 240p) копиями, исходный поток отдаётся без перекодирования | Есть |
| FR-5 | Поток может быть закрытым: страница, архив и чат доступны только по ссылке с ключом; закрытие потока и смена ключа мгновенно обрывают старый адрес | Есть |
| FR-6 | Организация может закрыть эфир из кабинета (кодер при этом не отключается; в ручном режиме с включённой записью эфир ставится на паузу); поток в эфире нельзя удалить | Есть |
| FR-7 | Реквизиты ингеста стабильны: адрес и порты не меняются при переезде платформы на другие серверы | План |

### 3.2 Просмотр

| Код | Требование | Статус |
|---|---|---|
| FR-10 | Зритель смотрит эфир в браузере без регистрации | Есть |

| FR-13 | Качество выбирается автоматически по ширине канала, вручную — из лесенки | Есть |
| FR-14 | Чат по каждому потоку; никнейм хранится в браузере; организация включает и выключает чат и задаёт срок жизни сообщений | Есть |
| FR-15 | Архив завершённых эфиров с плеером; записи не удаляются автоматически | Есть |

| FR-17 | Полноэкранный просмотр одной камеры, в том числе на iOS | Есть |

## 4. Нефункциональные требования

### 4.1 Производительность и масштабируемость

| Код | Требование | Сейчас | Статус |
|---|---|---|---|
| NFR-1 | 2 000 одновременных зрителей на эфир и 10 параллельных эфиров без деградации. Цифра итоговая, подтверждается нагрузочным тестом | ~250 зрителей на сервер — расчёт по каналу одного сервера | План |
| NFR-2 | Видео раздаётся не через API: сегменты пишутся в origin-хранилище, зрителям их отдаёт nginx; закрытые потоки — подписанный URL с коротким сроком. Варианты реализации: S3-совместимое хранилище или общий том | API отдаёт каждый сегмент с локального диска | План |
| NFR-3 | CDN перед origin: сначала перед текущим nginx (этап 1), после NFR-2 — перед origin-хранилищем | Нет | План |
| NFR-4 | Приём потоков и лесенка качеств на нескольких серверах (2–5); организации распределяются между ними. Варианты реализации: кодирование на видеокарте, если такие серверы дешевле | Один сервер, ~7 ядер на один 4K-эфир | План |
| NFR-5 | API без состояния в памяти процесса: чат, присутствие и счётчик зрителей — в Redis; экземпляров API и чата может быть несколько | Счётчик и мьютексы в памяти одного процесса | План |
| NFR-6 | Задержка live около 2 с (LL-HLS) после выноса доставки | Секунды, сегменты 2 с | План |

### 4.2 Доступность и выкладка

| Код | Требование | Статус |
|---|---|---|
| NFR-10 | Выкладка обновлений не обрывает приём: медиа-часть не перезапускается, пока идёт эфир; пауза раздачи при рестарте API — не больше 5 с | Есть |

## 6. Этапы

Порядок — по зависимостям, даты ориентировочные (диаграмма в
[`requirements-plan-gantt.png`](requirements-plan-gantt.png)):

1. Ноябрь–декабрь 2026: перенос платформы на новый сервер, CDN перед текущим nginx, прототип пульта организатора, дизайн и прототипы приложений.
2. Январь–май 2027: приложения до рабочих версий, автонарезка схваток и связка с секретарём.
3. Параллельно, в порядке зависимостей: измеренный потолок (NFR-43) до начала выноса; вынос раздачи видео (NFR-2) с переключением CDN на origin-хранилище (NFR-3), затем несколько медиа-серверов (NFR-4, NFR-5); разделение на сервисы и переделка CI/CD (NFR-40–NFR-42); метрики и трекинг ошибок (NFR-21, NFR-22).
4. Отдельным этапом после юридической подготовки: подписки и оплата (FR-61, FR-62).

Функции внедряются в уже работающий продакшн постепенно; отдельного
«запуска» нет.
