# Демо-ролик лендинга: сегментная раздача (HLS)

Блок «демонстрация системы» в hero лендинга (`InteractiveDemo`) играет ролик из
публичного бакета MinIO. С 07.09.2026 он раздаётся **HLS-сегментами**, а не
одним файлом.

## Почему пришлось менять

В бакете лежал один прогрессивный MP4:

| параметр | значение |
|---|---|
| разрешение | 3840×2180 |
| кодек | H.264 Main, **Level 5.1** |
| длительность | 16,2 с |
| размер | 101 618 730 Б (~97 МБ) |
| эффективный битрейт | **~50 Мбит/с** |

Отсюда обе жалобы:

- **iOS — «тяжело».** Файл отдавался целиком: до первого кадра телефон тянул
  десятки мегабайт. `moov` в начале (faststart есть), Range работает — но это
  не помогает, когда сам поток 50 Мбит/с.
- **Android — «не грузится вообще».** 4K H.264 Level 5.1 не проходит через
  аппаратный декодер большинства телефонов: 4K там обычно только HEVC/VP9/AV1.
  Софтовый декодер на таком битрейте захлёбывается.

Важно: **одной сегментации мало.** Если нарезать тот же 4K на сегменты, Android
по-прежнему не покажет картинку — упрётся в декодер. Поэтому лестница обрезана
сверху 2560 px, и каждая её ступень декодируется железом.

## Лестница

Собирается `infra/scripts/build-demo-hls.sh`, сегменты по 2 с, звука нет
(ролик и так `muted` + `loop`):

| ступень | битрейт | вес 16 с |
|---|---|---|
| 2560×1454 | 5,5 Мбит/с | ~11 МБ |
| 1920×1090 | 3,0 Мбит/с | ~6 МБ |
| 1280×728 | 1,5 Мбит/с | ~3 МБ |
| 854×486 | 0,8 Мбит/с | ~1,6 МБ |

Ступень выбирает ABR, а `capLevelToPlayerSize` в плеере не даёт взять больше,
чем помещается на экране (с учётом dpr). Телефон на быстром Wi-Fi получит
1280, а не 2560 — иначе он снова упёрся бы в декодер.

## Как пересобрать

На сервере, из корня чекаута:

```bash
./infra/scripts/build-demo-hls.sh
```

Источник по умолчанию — объект, который лендинг играл раньше
(`landing/demo-multicam-v1.mp4`). Новый ролик:

```bash
./infra/scripts/build-demo-hls.sh ./new-demo.mp4
```

Скрипт работает **внутри** уже запущенных контейнеров (`docker compose exec`):
ffmpeg берётся из `api`, `mc` — из `minio`. Жизненный цикл контейнеров не
трогается, ингест и запись не прерываются. Но транскод 4K нагружает CPU, и хотя
он идёт под `nice -n 19` с `THREADS=4`, **запускать лучше без эфира** — иначе
он конкурирует с FFmpeg'ами живых трансляций.

По завершении скрипт печатает готовую строку для `.env`. Дальше:

```bash
docker compose build web && docker compose up -d --no-deps web
```

Пересборка обязательна: `NEXT_PUBLIC_*` инлайнится на build-time, рестарт
значение не подхватит.

## Порядок выкатки не важен

Плеер выбирает ветку по расширению в `NEXT_PUBLIC_DEMO_VIDEO_URL`: `.m3u8` →
HLS, всё остальное → прежний `<video src>`. Поэтому код можно выкатить до
заливки сегментов (лендинг продолжит играть старый MP4), а переменную поменять
когда угодно после.

Пустая переменная — не поломка: блок покажет статичную заглушку, интерактив с
квадрантами продолжит работать.

## Версионирование каталога

Путь версионируется (`landing/demo-hls-v1`), потому что сегменты отдаются с
`Cache-Control: immutable` на год. Перезаливка **поверх того же пути** не
разойдётся по браузерам и CDN — при смене ролика меняйте версию:

```bash
DEST_PREFIX=landing/demo-hls-v2 ./infra/scripts/build-demo-hls.sh ./new-demo.mp4
```

Плейлисты кэшируются 5 минут — правку лестницы в пределах одной версии видно
почти сразу.

## Старый MP4

`landing/demo-multicam-v1.mp4` остаётся в бакете: он служит исходником для
пересборки. Удалять его стоит только вместе с заменой на новый исходник.
