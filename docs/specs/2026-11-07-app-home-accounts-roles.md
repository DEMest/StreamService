# Приложение зрителя и организатора: главный экран, аккаунты, каналы и роли

Дата: 7 ноября 2026. Статус: **черновик**, формулировки уточняются с
заказчиком. Первый из серии документов, которые по частям пересматривают
[`../srs.md`](../srs.md): здесь — только вход в приложение, главный экран
и модель аккаунтов, каналов и ролей. Нагрузка, разделение на сервисы,
переезд на серверы и метрики (разделы 4 и 6 SRS) не меняются и здесь не
обсуждаются.

Коды требований продолжают нумерацию SRS: FR-100 и дальше, NFR-60 и
дальше. Статусы те же: **Есть** / **План** / **Возможно**.

## 1. Что меняется относительно SRS

| Было в SRS (октябрь 2026) | Становится |
|---|---|
| Два мобильных приложения: зрителя (§3.5) и организатора (§3.6) | **Одно приложение.** У всех один сплеш, один вход и один главный экран; аккаунту организатора на главном экране добавляется раздел **«Студия»** с теми же функциями, что сегодня в веб-кабинете. Захват камер, NDI и плагины (FR-50, FR-51, FR-54) остаются отдельной задачей и в этот документ не входят |
| Зритель без аккаунта (FR-10, FR-60) | Просмотр в браузере остаётся без регистрации. **В приложении аккаунт обязателен**: сплеш ведёт либо на главный экран, либо на вход. Профиль зрителя из FR-43 становится этим аккаунтом |
| Вход есть только у организации (логин = slug), суперадмина и рекламного менеджера | Появляется **аккаунт человека**. Организация становится тем, чем аккаунт *владеет*, а не тем, чем он *входит*. Существующие организации получают аккаунт с тем же логином и паролем — переход незаметен |
| Канал (Stream) принадлежит только организации | У **каждого** аккаунта есть канал. У организатора он публичный, у зрителя — **безликий**: не виден ни в каталоге, ни на странице организации, ни в поиске и не индексируется. Каналы получают **категорию** |
| Ролей три: `superadmin`, `org_admin`, `ad_manager` | Аккаунт может получить **дополнительные роли**: «Школа», «Участник соревнований». Это сущности с расширяемым набором качеств, а не флаги |
| Событие (турнир) — название, дата, число ковров (FR-30) | Турнир получает **регистрацию участников**: участника регистрирует организатор или школа. Это событие внутри сервиса; как регистрация устроена в реальном мире, пока неизвестно |

## 2. Термины

| Термин | Значение |
|---|---|
| Аккаунт | Учётная запись человека в приложении и на сайте: логин, пароль, профиль. Один аккаунт — один человек |
| Организатор | Аккаунт, владеющий хотя бы одной организацией. Только ему показывается «Студия» |
| Зритель | Любой аккаунт, у которого нет организации. Зритель может стать организатором, не заводя новый аккаунт |
| Канал | То, что сегодня называется Stream: единица трансляции со своим ключом ингеста, приватностью, записью и архивом. Каждый канал имеет **категорию** |
| Безликий канал | Канал категории `personal`: существует у каждого зрителя, но нигде не показывается. Носитель идентичности зрителя в чате, подписках и ролях |
| Роль | Дополнительное качество аккаунта: «Школа», «Участник соревнований». У роли есть набор атрибутов, который расширяется без миграции схемы |
| Турнир | Событие из FR-30: название, дата, площадки; к нему привязаны каналы, эфиры, записи, клипы и **регистрации участников** |
| Регистрация | Запись «участник X заявлен на турнир Y тем-то». Создаётся организатором турнира или школой участника |
| Студия | Раздел главного экрана организатора: всё, что сегодня есть в веб-кабинете `/dashboard` |

## 3. Сценарии

### 3.1 Сплеш и вход

```
запуск приложения
      │
      ▼
   СПЛЕШ ── есть сохранённая сессия? ──нет──► ВХОД ◄──► РЕГИСТРАЦИЯ
      │                                         │
     да                                         │ успех
      │ сессия действительна                    │
      ▼                                         ▼
 ГЛАВНЫЙ ЭКРАН ◄────────────────────────────────┘
      │
      └── Профиль → «Выйти» / «Сменить аккаунт» ──► ВХОД
```

1. Сплеш один для всех — на нём нет выбора «я зритель / я организатор».
   Приложение молча проверяет сохранённую сессию (`GET /v1/auth/me`, при
   просроченном access — `POST /v1/auth/refresh`).
2. Сессия действительна → главный экран, без единого нажатия. Сессия
   отозвана или её нет → экран входа.
3. API недоступен, а сессия сохранена → главный экран в режиме «нет сети»
   с кнопкой повтора; выход и смена аккаунта доступны и оттуда. Приложение
   не должно упираться в сплеш из-за сервера.
4. Выйти и войти другим аккаунтом (в том числе зарегистрировать новый)
   можно всегда — из профиля на главном экране. Выход отзывает refresh-токен
   на сервере и стирает сессию на устройстве.
5. Регистрация: e-mail и пароль, подтверждение письмом (SMTP уже есть,
   FR-80). Телефон и вход через сторонние сервисы — открытый вопрос (§7).

### 3.2 Главный экран

Один экран, набор разделов зависит от аккаунта:

| Раздел | Зритель | Организатор | Что внутри |
|---|---|---|---|
| Эфиры | да | да | Каталог организаций и трансляций в эфире, страница турнира (FR-40) |
| Архив и клипы | да | да | Записи и вертикальная лента клипов (FR-42) |
| Поиск | да | да | По организации, турниру, спортсмену (FR-33, FR-40) |
| Профиль | да | да | Аккаунт, подписки на организации (FR-43), роли (§3.4), выход и смена аккаунта |
| **Студия** | нет | **да** | Веб-кабинет организации целиком: каналы и их настройки (FR-20, FR-21), живая статистика эфира (FR-22), записи и место в архиве (FR-23), пульт и турниры (FR-24, FR-30), настройки организации и чата |

«Студия» появляется в момент, когда аккаунт становится организатором, и
исчезает, когда перестаёт им быть; перезапуск приложения не нужен — права
приходят из `/v1/auth/me`. Разделы, которые зритель и организатор видят
одинаково, и ведут себя одинаково: организатор смотрит чужие эфиры как
зритель.

### 3.3 Каналы

- При создании аккаунта создаётся его **безликий канал** (`personal`).
  Зритель его не видит как «канал», но именно он хранит никнейм для чата
  (вместо localStorage, FR-14), подписки и роли.
- Организатор, как и сегодня, заводит в «Студии» сколько угодно каналов
  категории `organizer`; они показываются на странице организации, в
  каталоге, поиске и sitemap по действующим правилам (FR-16, FR-81).
- Каналы категорий `school`, `participant` и `tournament` появляются вместе
  с ролью или турниром (§3.4, §3.5). Их видимость — по той же категории:
  правило «показывать или нет» живёт в одном месте на бэкенде рядом с
  правилом индексации (NFR-45).
- Что зритель может делать со своим безликим каналом сверх чата и подписок
  (например, вести эфир с телефона, FR-50) — открытый вопрос (§7).

### 3.4 Роли «Школа» и «Участник соревнований»

- Роль запрашивается из профиля любым аккаунтом, зрителем или организатором.
  У аккаунта может быть несколько ролей; одна и та же роль дважды не
  выдаётся.
- Роль — сущность с **расширяемым набором атрибутов**: у «Школы» —
  название, город, тренер, контакт; у «Участника» — фамилия, имя, год
  рождения, весовая категория, школа. Набор не окончательный: атрибуты
  хранятся как документ, а в колонки схемы выносится только то, по чему
  нужен поиск (фамилия участника — для FR-33).
- Кто подтверждает роль — сам аккаунт (самодекларация), организатор или
  суперадмин — открытый вопрос (§7). До решения роль считается
  подтверждённой при создании.
- Роль может иметь свой канал соответствующей категории: у школы — страница
  школы с её эфирами и участниками, у участника — его клипы со всех турниров
  (результат автонарезки FR-32 раскладывается по участникам, это и есть
  ответ на боль H2 из исследования аудитории).

### 3.5 Турнир и регистрация участников

- Турнир создаёт организатор в «Студии» (FR-24, FR-30). К турниру
  привязываются каналы категории `tournament`; это те же Stream'ы с тем же
  ингестом, просто с другой категорией и ссылкой на турнир.
- Участника на турнир регистрирует **организатор турнира** или **школа**,
  к которой участник привязан. Сам участник заявку не подаёт — пока это
  осознанное упрощение, чтобы не проектировать модерацию.
- Регистрация хранит: турнир, участника, кто зарегистрировал, когда,
  статус. Статусы на старте — `registered` и `withdrawn`; подтверждение и
  отклонение добавляются, когда станет понятен реальный процесс.
- Список зарегистрированных участников — вход для секретаря (FR-31) и для
  подписи клипов (FR-32): фамилия на клипе берётся из регистрации, а не
  вводится руками второй раз.

## 5. Модель данных и миграция с текущей схемы

Исходная точка — `prisma/schema.prisma`: `User` (суперадмин, рекламный
менеджер), `Organization` с собственным `passwordHash`, `Stream`,
`Broadcast`, `Recording`, `ChatMessage`. Всё ниже добавляется поверх неё;
ни одна существующая таблица не переименовывается.

```
Account ──владеет──► Organization ──► Stream (category) ──► Broadcast ──► Recording
   │                       │                 ▲
   │                       └── Event ────────┘  (category = tournament)
   │                             │
   │                             └── Registration ──► AccountRole (participant)
   │
   └── AccountRole (school | participant) ──► Stream (category = school | participant,
                                                      orgId = personal-организация аккаунта)
```

Инвариант «каждый Stream принадлежит Organization» сохраняется: канал
школы или участника лежит под скрытой `personal`-организацией того же
аккаунта, а не вне тенантности.

| Таблица | Изменение | Зачем |
|---|---|---|
| `Account` | **Новая**: `id`, `email` (unique), `passwordHash`, `displayName`, `emailVerifiedAt`, `createdAt` | Аккаунт человека. Не расширяем `User`: там живут служебные роли платформы с другим жизненным циклом и другим поддоменом входа |
| `Organization` | `+ownerAccountId` (nullable на время миграции), `+kind` = `organizer` \| `personal` | Владение и «организаторство». `personal` — скрытый арендатор зрителя: так безликий канал живёт в той же модели `Organization → Stream`, и `/v1/org/*`, пути ингеста `live/<slug>/<stream>`, запись, чат и приватность работают без второй ветки кода. `slug` и `name` у неё генерируются (`u-<id аккаунта>`), не выбираются человеком и не пересекаются ни с публичными слагами, ни с `RESERVED_STREAM_SLUGS`. Вместе с ней создаётся её единственный Stream `personal` — осознанное исключение из правила «новая организация без Stream'ов», которое для `organizer` остаётся в силе |
| `Organization.passwordHash` | Остаётся, пока есть организации без `ownerAccountId`; `AuthService.login` пробует `Account`, затем, как сегодня, `Organization` по slug | Плавный переход: ни одна организация не теряет вход в день выкатки |
| `Stream` | `+category` = `organizer` \| `personal` \| `school` \| `participant` \| `tournament` (default `organizer`), `+eventId` (nullable) | «Новые категории в таблице каналов». Бэкфилл: все существующие строки — `organizer` |
| `AccountRole` | **Новая**: `id`, `accountId`, `kind` (`school` \| `participant`), `attributes Json`, `searchName` (nullable, индекс), `schoolRoleId` (nullable, self-relation для участника), `streamId` (nullable), `createdAt`; `@@unique([accountId, kind])` | Роль с расширяемыми атрибутами; поиск по фамилии через `searchName` |
| `Event` | **Новая**, из FR-30: `id`, `orgId`, `title`, `startsAt`, `endsAt`, `venueCount`, `createdAt` | Турнир. Таблица с таким именем уже была и удалена миграцией `20260702000000_drop_event` вместе с `EventStream` (M:N). Это повторное введение с другой связью — `Stream.eventId` 1:N; старую миграцию не трогать, только новая вперёд |
| `Registration` | **Новая**: `id`, `eventId`, `participantRoleId`, `registeredByAccountId`, `status`, `createdAt`; `@@unique([eventId, participantRoleId])` | Заявка участника на турнир |
| `ChatMessage` | `+accountId` (nullable) | Сообщение авторизованного зрителя привязано к аккаунту; гость на сайте — как сегодня, по никнейму |
| JWT | `role: 'account'` с `accountId`, список `orgIds` владения; `org_admin` остаётся для не мигрировавших организаций | Клиент решает про «Студию» по наличию организаций в `/v1/auth/me` |

Порядок миграции (шаги 1 и 3 — схемные миграции в `prisma/migrations/`,
шаг 2 — идемпотентный скрипт в `prisma/data/004-*.ts`, как остальные
бэкфиллы проекта; каждый шаг обратим):

1. Таблицы `Account`, `AccountRole`, `Event`, `Registration`; колонки
   `Organization.ownerAccountId`, `Organization.kind`, `Stream.category`,
   `Stream.eventId`, `ChatMessage.accountId` — все nullable или с default.
2. Бэкфилл: на каждую `Organization` — `Account` с `email = <slug>@legacy.local`
   (или настоящий e-mail, если организация его сообщила), `passwordHash`
   копируется, `ownerAccountId` проставляется, `kind = organizer`; все
   `Stream` — `category = organizer`.
3. Вход через `Account`; `Organization.passwordHash` помечается
   устаревшим. Удаляется отдельной миграцией, когда организаций без
   владельца не останется — по тому же правилу, что `ChatMessage.orgId`.

Что при реализации меняется в зафиксированных сегодня фактах `CLAUDE.md` и
правится вместе с кодом: никнейм чата хранится на клиенте (FR-123); список
ролей JWT и таблица разделов `apps/web/src/lib/sections.ts` с проверкой в
`middleware.ts` (новая роль `account`); правило «новая организация без
Stream'ов» (исключение для `personal`).

## 6. Интерфейсы API (эскиз)

| Маршрут | Назначение | Кто |
|---|---|---|
| `POST /v1/auth/register`, `POST /v1/auth/verify-email`, `POST /v1/auth/forgot-password` | Регистрация и восстановление | без авторизации |
| `POST /v1/auth/login`, `/refresh`, `/logout`, `GET /v1/auth/me` | Как сегодня; `me` дополнительно отдаёт `organizations[]` и `roles[]` | cookie или Bearer |
| `GET/PATCH /v1/me`, `GET/POST/DELETE /v1/me/roles` | Профиль и роли аккаунта | аккаунт |
| `GET/POST /v1/me/subscriptions` | Подписки на организации (FR-43) | аккаунт |
| `/v1/org/*` с выбором организации | Текущий кабинет; организация берётся из токена, при нескольких — из заголовка или пути | владелец организации |
| `GET/POST /v1/org/events`, `GET/POST/DELETE /v1/org/events/:id/registrations` | Турниры и регистрации организатора | владелец организации |
| `GET/POST/DELETE /v1/me/roles/school/registrations` | Регистрации участников школой | аккаунт с ролью «Школа» |
| `GET /v1/public/events/:id`, `GET /v1/public/participants/:id` | Страница турнира, страница участника с клипами | без авторизации |

Все клиенты ходят в одно API (SRS §2.3) — отдельного слоя для приложения
не появляется.
