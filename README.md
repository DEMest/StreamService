# StreamService — Liga Live

Платформа для видеотрансляций спортивных турниров (по борьбе — стартовая ниша,
архитектура не завязана на конкретный вид спорта). Организация подключает
видеомикшер (vMix/OBS), отправляет один поток на сервер — зрители смотрят
трансляцию в браузере, переключают ракурсы камер, общаются в чате и потом
пересматривают эфир в архиве.

Продакшн: **[liga-live.ru](https://liga-live.ru)**

## Архитектура

**Ключевой принцип: сервер не транскодирует и не пересобирает исходный поток.**
Организация шлёт один SRT- или RTMP-поток (одна композитная картинка — например,
раскладка 2×2 с четырёх камер, собранная в vMix, — либо один ракурс). Всё
переключение между камерами происходит на стороне зрителя: браузер декодирует
единственный HLS-поток через `hls.js` и рисует нужную часть кадра на
`<canvas>` (`requestAnimationFrame` + `drawImage`, letterboxed crop). Экономия
принципиальная: N зрителей = N декодирований одного и того же потока, а не
N раздельных стримов с сервера.

```
Кодер стримера (vMix / OBS)
        │  SRT :8890  или  RTMP :1935 — один поток на Stream
        ▼
   MediaMTX (Docker)
        │  authMethod: http → POST /v1/internal/mediamtx/auth
        │  (SRT — passphrase на уровне транспорта; RTMP — ingestKey Stream'а)
        │
        ├─ record: yes → fmp4-сегменты по 3 часа → /recordings (диск, временно)
        │
        └─ runOnReady → on-ready.sh:
                 запускает FFmpeg, который тянет rtsp://localhost:8554/<path>
                 и пишет ABR-лесенку HLS: 1080p (copy) + 720p/480p/240p
                 (libx264, транскод) → /hls/<path> (общий Docker-том)
                                    │
                                    ▼
                     NestJS API отдаёт live HLS
                (previewKey-гейтинг для приватных трансляций,
                 Cache-Control: no-store — сегменты ротируются)
                                    │
                                    ▼
                 nginx (TLS, кэш сегментов) ──► браузер
                                                    │
                                     hls.js декодирует один поток →
                                     <canvas> рисует нужный кадр
                                     (весь кадр, либо квадрант 2×2)
```

После эфира сегменты переезжают в архив: HLS-VOD плейлист собирается через
`ffprobe`/`ffmpeg -c copy` (без перекодирования), единый MP4 для скачивания
склеивается один раз, всё заливается в S3-совместимое хранилище, а локальный
scratch удаляется. Подробнее — [«Архив трансляций и хранилище»](#архив-трансляций-и-хранилище).

Обработка вебхука публикации/остановки эфира на стороне API сериализована
мьютексом на каждый Stream — это исключает гонку «двойного Broadcast» при
частых реконнектах кодера.

## Мультиарендность: Organization → Stream → Broadcast

- **Organization** — арендатор (спортивная организация/лига). Логин/пароль,
  настройки чата (`chatTtlMinutes`, `chatEnabled`), картинка для карточек каталога.
- **Stream** — единица трансляции внутри организации: свой ingest-ключ (SRT
  passphrase / RTMP-ключ, можно перевыпустить), приватность (`isPublic` +
  `previewKey` для доступа по ссылке), режим записи (`auto`/`manual`),
  режим показа (`composite` — раскладка с квадрантами, `single` — один
  ракурс без кропа). У организации может быть несколько Stream'ов
  (например, разные площадки/маты турнира).
- **Broadcast** — одна сессия эфира конкретного Stream'а: создаётся на первый
  publish, закрывается на последний unpublish. Хранит связанные записи.
- **Recording** — готовая запись эфира в архиве: статус, путь в S3, размер,
  длительность, срок хранения.
- **ChatMessage** — сообщения чата, привязаны к Stream'у.

Все `/v1/org/*` эндпоинты фильтруются по `orgId` пользователя; попытка
достучаться до чужого Stream'а возвращает 404 (существование не палится).

## Кто что видит: роли и возможности

### Зритель (без входа)
- Каталог организаций и трансляций, живой поиск по сайту (организации,
  стримы, записи — только то, что и так публично видно анониму).
- Просмотр эфира: ABR-качество (1080p/720p/480p/240p, автопереключение по
  ширине канала), при композитной раскладке — переключение между общим видом
  и отдельными камерами.
- Живой чат по каждой трансляции (никнейм хранится локально в браузере).
- Архив завершённых эфиров с HLS-VOD плеером и скачиванием MP4.
- Форма обратной связи (жалоба/вопрос по конкретному эфиру — тема, текст,
  необязательный контакт для ответа).

### Организация (`org_admin`, вход по логину/паролю)
- Личный кабинет (`/dashboard`): список своих Stream'ов, создание/переименование/
  удаление, картинка организации (с кропом 16:9), настройки чата (TTL,
  вкл/выкл), карточка расхода места в архиве с прогнозом (с поправкой на
  двойной пик места на диске в момент заливки в S3).
- Экран Stream'а (`/dashboard/streams/[id]`) — студия и настройки: SRT/RTMP
  реквизиты для кодера (сгенерированные строки подключения, ключ можно
  скрыть/показать/перевыпустить), режим приватности, автостарт-режим
  (`public`/`test` — тестовый эфир не попадает в публичный каталог),
  вкл/выкл и режим записи.
- Живая статистика эфира: входящий битрейт, кодек/разрешение видео и аудио,
  для SRT — потери пакетов и RTT, для транскодера — fps/speed/дропнутые
  кадры (сигнал «сервер не успевает кодировать»).

### Суперадмин (`superadmin`) — [«Админка»](#админка)
- Управление организациями, заявками с лендинга, обращениями обратной связи,
  экраном ёмкости сервера.

## Админка

«Админка» — это `/admin` и три вложенных экрана, доступные только роли
`superadmin` (логин/пароль заводится автоматически при старте API из
`SUPERADMIN_LOGIN`/`SUPERADMIN_PASSWORD`):

- **`/admin`** — организации: создать (логин + пароль, название организация
  меняет сама в своём кабинете), включить/отключить, удалить.
- **`/admin/requests`** — заявки с формы на лендинге «Подключите вашу
  организацию»: имя, организация, email/телефон (кликабельны), сообщение.
  Статусы «новая»/«обработана», можно удалить.
- **`/admin/feedback`** — обращения обратной связи от зрителей/организаторов:
  тема, текст, технический контекст (URL страницы, организация, стрим,
  user-agent) — чтобы жалобу «тормозит видео» можно было разобрать не
  переспрашивая.
- **`/admin/capacity`** — см. [«Метрики ёмкости сервера»](#метрики-ёмкости-сервера-и-qoe).

## Архив трансляций и хранилище

Запись включается по Stream'у (`recordingMode`: `auto` — начинается
автоматически с первым publish, `manual` — включает организация). MediaMTX
пишет сырые fmp4-сегменты на диск; после окончания эфира:

1. Сегменты переименовываются в стабильный формат и получают HLS-VOD
   плейлист (`buildHlsVodPlaylist`/`buildMasterPlaylist`) — без перекодирования.
2. Из тех же сегментов один раз собирается единый MP4 для скачивания
   (`ffmpeg -c copy`).
3. Кадр из середины первого сегмента становится превью записи (если не
   загружено вручную).
4. Готовый архив (плейлисты + MP4 + превью) потоковой multipart-заливкой
   уходит в S3-совместимое хранилище; финализация записи (`status='ready'`)
   происходит **только** после успешной заливки — иначе запись осталась бы
   помечена готовой без объекта в хранилище.
5. Локальный scratch удаляется. Просмотр и скачивание идут по presigned-ссылкам
   (подпись строится против публичного endpoint'а хранилища, а не
   внутреннего docker-адреса).

Срок хранения записи — **7 дней** (`RECORDING_RETENTION_DAYS`), крон в
03:00 сносит просроченные записи из хранилища и базы. Отдельный крон в
03:30 повторяет неудавшиеся конверсии/заливки; если заливка на первой
попытке уже была сделана, повтор возобновляет именно её — не пересобирает
архив с нуля. Осиротевшие директории (запись есть на диске, но нет в базе —
например, после падения API посреди конверсии) подчищаются при старте API.

## Метрики ёмкости сервера и QoE

`/admin/capacity` отвечает на вопрос «сколько зрителей выдержит канал сервера
прямо сейчас и нужен ли уже CDN» — на трёх независимых источниках данных:

- **Отдача** — фактический трафик и попадания в кэш **из лога nginx**
  (кэш нарочно не пускает запросы сегментов дальше, поэтому это единственная
  точка, которая видит реальную отдачу зрителям).
- **Кодирование** — худшая скорость кодирования (`speed`) среди идущих
  эфиров, из progress-файла FFmpeg; ниже порога — зрители уже видят рывки.
- **QoE с плееров** — телеметрия от самих браузеров зрителей: подвисания
  буфера, время загрузки фрагмента (P95, не среднее — иначе страдания
  худших зрителей размываются по всем), фактическая ступень ABR-лесенки.

Из этого считается заполнение исходящего канала (`UPLINK_MBPS`, единственное
число, которое неоткуда измерить программно, — вводится вручную), потолок по
одновременным зрителям с запасом на ингест/чат/всплески (`CAPACITY_HEADROOM`),
и открываются/закрываются инциденты (`uplink`/`encode`/`errors`/`stalls`/`offline`)
с историей за час (в памяти), сутки и неделю (в базе, минутные срезы).
Разовая инфраструктурная настройка (общий том с логом nginx) описана в
[`docs/capacity-metrics-setup.md`](docs/capacity-metrics-setup.md). Алерты
дублируются в письмо и опционально в Telegram.

## SEO и индексация

Единственный источник правды — бэкенд (`apps/api/src/seo/`): решение
«индексировать ли страницу» одинаково питает и `sitemap.xml`, и мета-тег
`robots` на самой странице, чтобы карта сайта и сама страница никогда не
противоречили друг другу.

- **Что индексируется.** Статические разделы всегда; организация или Stream —
  только «живые» (идёт эфир или была хотя бы одна завершённая публичная
  трансляция). Пустая организация получает `noindex` и не попадает в sitemap.
  Приоритет по свежести: live 0.9 → эфир за 30 дней 0.7 → давние 0.5.
- **Приватные трансляции** (по `previewKey`) не отдаются в поиске по имени
  ни через sitemap, ни через `page-meta`; `robots.txt` дополнительно закрывает
  `*?key=`.
- **JSON-LD**: `WebSite`+`Organization` на всех страницах, `VideoObject` с
  `publication: BroadcastEvent` на странице трансляции — это не украшение,
  Google Indexing API принимает только страницы с такой разметкой.
- **Пинг поисковикам** при фактической смене состояния эфира: IndexNow
  (Яндекс, Bing) — для страницы трансляции и списков, Google Indexing API —
  для страницы трансляции. Троттлинг 10 минут на URL защищает от
  «мигающего» ингеста и от суточной квоты Google (200 URL/сутки).
  Всё fire-and-forget — недоступность поисковика не влияет на эфир.
- **Поиск по сайту** (`/search`) индексирует то же самое, что видно анониму:
  организации, публичные Stream'ы, записи завершённых публичных эфиров.

## Правовая часть

`apps/web/src/lib/legal.ts` — единый источник реквизитов и текущей редакции
документов для всего фронтенда:

- **Политика конфиденциальности** и **пользовательское соглашение**
  (`/legal/privacy`, `/legal/terms`).
- **Страница для правообладателей** (`/legal/copyright`) — обращение по
  ст. 15.7 149-ФЗ.
- **Версионирование согласия**: заявка с лендинга и обращение обратной связи
  фиксируют не «текущую» редакцию документов, а ту, которую человек
  действительно видел в момент согласия (`consentAt`/`consentVersion` в
  `ContactRequest` и `Feedback`).
- Единый публичный контакт (`info@liga-live.ru`, псевдонимы `postmaster@`/
  `abuse@`/`support@`) стоит и в правовых документах, и как получатель
  претензий правообладателей.

## Почта, домен и сертификаты

Домен **liga-live.ru** зарегистрирован и обслуживается в **Рег.ру**:

- **DNS** — A-запись на IP сервера настроена в панели Рег.ру.
- **SSL** — сертификат выпущен через Рег.ру, вручную установлен на сервере
  (`/etc/ssl/regru/`), TLS терминирует nginx перед Docker-стеком.
- **Почта** — у домена уже стоял MX на почтовый хостинг Рег.ру (с готовыми
  DKIM/DMARC и прогретой репутацией отправляющего IP), поэтому у проекта
  **нет собственного MTA**: транзакционные письма (заявки, обратная связь,
  оповещения о деплое, тревоги ёмкости) уходят через SMTP-ящик на
  `mail.hosting.reg.ru`. Свой релей потребовал бы PTR-записи, открытого
  исходящего 25 порта (большинство хостеров режут его по умолчанию) и
  приёма входящей почты — ради нескольких служебных писем в день это того
  не стоило.
- Если SMTP не настроен — заявки и обращения продолжают копиться в админке,
  просто без письма; ничего не ломается.

## Инфраструктура и деплой

**Docker Compose** поднимает: `postgres`, `minio` (S3-совместимое хранилище
архива), `mediamtx` (ингест + запись), `api`, `web`. Наружу торчит только
ингест (SRT/RTMP) и то, что явно проксирует внешний nginx — сами `api`/`web`
доступны только внутри Docker-сети `edge`.

**CI/CD** — GitHub Actions на self-hosted раннере (тот же хост, что и прод):

- На каждый PR и на `main` — сборка + типы + тесты API, сборка + типы веба.
- Мерж в `main` → деплой: раннер заходит на прод по SSH и запускает
  `infra/deploy/deploy.sh`. Пересобираются и перезапускаются только `api` и
  `web` (`--no-deps`) — MediaMTX не трогается, поэтому идущий приём эфира,
  ABR-транскод и запись не прерываются деплоем.
- Единственный заметный эффект — отдача live HLS ставится на паузу на
  ~5 секунд, пока перезапускается API (сам отдаёт HLS). При сегментах по 2 с
  и окне плейлиста 80 с, плюс отдаче nginx устаревшего сегмента при ошибке
  апстрима, зрители обычно не замечают, и трансляция не обрывается.
- Изменения `infra/mediamtx/*` или `docker-compose.yml` требуют перезапуска
  MediaMTX (обрывает приём у **всех** стримеров). Скрипт деплоя сам решает:
  нет живых эфиров → перезапускает вместе с остальным; есть эфиры и форс не
  запрошен → **деплой останавливается и ничего не меняет**, следующий пуш
  повторит попытку; форс можно запросить явно через ручной запуск workflow.
- Все side-effect'ы деплоя защищены health-gate с откатом на предыдущую
  версию при неудаче.

## Агентная разработка и деплой

Код в репозиторий в основном попадает не «руками», а через AI-агента
(Claude Code), которому задача ставится одним промптом на естественном языке
— дальше весь путь от постановки до релиза на проде проходит без ручных
промежуточных шагов:

1. **Агент исследует код и пишет реализацию**, следуя зафиксированным в
   `CLAUDE.md` архитектурным решениям проекта (принцип «без серверного
   транскода основного фида», границы мультиарендности, соглашения по
   git-флоу и т.д.), не изобретая лишних абстракций сверх задачи.
2. **Перед тем как считать задачу готовой**, агент прогоняет изменения через
   цепочку специализированных проверяющих под-агентов (`.claude/agents/`):
   - `task-completion-validator` — реально ли фича работает (сборка, тесты,
     код есть в диффе), а не «должна работать»;
   - `qa-browser-tester` — открывает интерфейс в браузере и проходит сценарий,
     если менялся фронтенд;
   - `claude-md-compliance` — сверяет изменения с зафиксированными
     соглашениями проекта;
   - `code-quality-pragmatist` — ловит переусложнение и тихие нарушения
     архитектуры;
   - `live-safety-auditor` — специфика именно этого проекта: сервер почти
     всегда отдаёт идущую трансляцию, поэтому перед мержем отдельный агент
     оценивает, не оборвёт ли изменение эфир. `FAIL` от него — жёсткий стоп,
     мерж не идёт.
3. Открывается PR, агент дожидается зелёного CI (сборка + тесты API и веба) и
   **сам мержит** — ручное подтверждение каждого мержа не требуется, это
   принятый в проекте дефолт.
4. **Мерж в `main` — это и есть релиз.** Отдельного шага «задеплоить» нет:
   мерж сам запускает деплой на проде (см. выше) с health-gate и защитой от
   обрыва идущего эфира.

Ручное вмешательство остаётся только там, где решение действительно должен
принимать человек: необратимые операции, форс-рестарт MediaMTX под идущим
эфиром и подобные исключения.

## Что реализовано

- Приём SRT/RTMP, ABR-лесенка HLS (1080p copy + 720p/480p/240p transcode),
  композитная 2×2 раскладка с клиентским кропом на `<canvas>`.
- Мультиарендность: организации, несколько Stream'ов на организацию,
  приватные трансляции по ссылке (`previewKey`).
- Запись эфиров: HLS-VOD архив + скачиваемый MP4, хранение в S3-совместимом
  объектном хранилище, срок жизни 7 дней, retry упавших заливок.
- Живой чат на WebSocket, настраиваемый TTL по организации.
- Личный кабинет организации: управление Stream'ами, ingest-реквизиты,
  живая статистика эфира, прогноз расхода места в архиве.
- Админка суперадмина: организации, заявки с лендинга, обратная связь,
  ёмкость сервера с историей и инцидентами.
- SEO: динамические sitemap/robots на едином правиле индексации, JSON-LD,
  пинг IndexNow + Google Indexing API, поиск по сайту.
- Правовые документы с версионированием согласия, лендинг с формой заявки.
- CI/CD с автодеплоем, health-gate, безопасным перезапуском MediaMTX.

Пока не реализовано (упоминалось в более ранних планах архитектуры, но
отсутствует в текущем коде): раздельные N-камерные потоки с серверными
layout-пресетами (сейчас — один композитный поток с клиентским кропом
квадрантов) и сущность «Событие», объединяющая несколько Stream'ов общим
чатом/лендингом.

## Локальный запуск

```bash
cp .env.example .env
docker network create edge   # один раз, если сети ещё нет
docker compose up -d --build
```

Сервисы: веб — `:3000` (порт из `WEB_PORT`), API — за nginx/веб-проксёй,
SRT-ингест — `:8890/udp`, RTMP — `:1935`.

Без Docker (веб/API нативно, MediaMTX — в контейнере):

```bash
pnpm install
pnpm dev:web          # apps/web на :3000
pnpm dev:api          # apps/api на :3001 (грузит ../../.env)
docker compose up -d mediamtx postgres minio
```

Тесты API (Jest, `apps/api`):

```bash
pnpm --filter api test
pnpm --filter api test -- --testPathPattern=stream
```

Фронтенд-тестов нет — проверка ручная, в браузере.

## Переменные окружения

Полный список с комментариями — в [`.env.example`](.env.example) и в
[`CLAUDE.md`](CLAUDE.md#environment-variables). Один `.env` обслуживает и
прод, и тест-стенд — отличие только в значениях (порты, публичные URL,
`COOKIE_SECURE`). Ключевые группы:

- Подключение к БД, JWT-секрет, CORS.
- Порты и адрес MediaMTX Control API.
- `S3_*` — S3-совместимое хранилище архива (endpoint внутренний и публичный,
  ключи, бакет).
- `SMTP_*`/`MAIL_*` — почта через хостинг регистратора домена.
- `SITE_URL`, `GOOGLE_SITE_VERIFICATION`, `YANDEX_VERIFICATION`,
  `INDEXNOW_KEY`, `GOOGLE_INDEXING_CREDENTIALS` — SEO/индексация.
- `UPLINK_MBPS`, `CAPACITY_HEADROOM`, `NGINX_LOG_PATH`, `TELEGRAM_*` —
  метрики ёмкости сервера.
- `HLS_LQ_ENABLED` — выключить ABR-лесенку до одной HD-копии на слабых
  стендах.
