# Принцип развития: от веба к приложению

Дата: 7 ноября 2026. Документ задаёт порядок, в котором развиваются клиенты
платформы Liga Live. Требования — в [`srs.md`](srs.md) и спеках по частям в
[`specs/`](specs/); здесь — правило, по которому эти требования попадают на
сайт и в приложение.

---

## 1. Суть

**Веб — эталон.** Сайт liga-live.ru работает в продакшне, и всё, что на нём
есть, зафиксировано: это базовый набор функций и поведения платформы.
Приложение для iOS и Android повторяет этот набор, а не придумывает свой.

Отсюда три правила:

1. **Что есть на вебе — фиксируем.** Текущее поведение сайта считается
   требованием. Приложение воспроизводит его: те же разделы, те же правила
   доступа, тот же порядок действий. Навигация и элементы управления
   нативные, смысл — тот же.
2. **Новое идёт через веб.** Новая функция описывается в спеке, делается в
   API и на сайте, и только потом переносится в приложение. Сайт и
   приложение не расходятся по составу функций дольше, чем длится перенос.
3. **Изменение веба — изменение требования.** Если поведение сайта меняется,
   это правка SRS или спеки, и она дублируется в приложение тем же порядком.

---

## 2. Порядок работы над функцией

| Шаг | Что делается | Результат |
|---|---|---|
| 1 | Спека: сценарий, требования, модель данных | Документ в `specs/`, коды требований в SRS |
| 2 | API и миграции | Эндпоинты, которыми будут пользоваться оба клиента |
| 3 | Веб | Функция работает на сайте в продакшне |
| 4 | Приложение | Тот же сценарий на iOS и Android поверх того же API |
| 5 | Проверка паритета | Поведение в приложении сверено с сайтом |

Шаги 3 и 4 могут идти параллельно у разных команд, если API готово и
сценарий на вебе согласован. Готовой функция считается, когда она есть на
обоих клиентах.

---

## 3. Что из этого следует

- **Одно API.** Оба клиента ходят в одни и те же эндпоинты; отдельного
  слоя для приложения нет. Если приложению нужно то, чего нет у веба, это
  повод сначала решить, нужно ли это вебу.
- **Правила живут на бэкенде.** Доступ к закрытым потокам, видимость
  каналов и личных страниц, индексация, роли — решает сервер. Клиенты их
  не дублируют и не проверяют сами.
- **Клиентские константы — копия веба.** То, что по природе живёт на
  клиенте (карта квадрантов композита, раскладки нескольких потоков),
  в приложении повторяет веб один в один и сверяется с ним при изменении.
- **Тексты и правовые документы — общие.** Политика конфиденциальности,
  соглашение и их редакция одни на сайт и приложение; согласие, данное на
  одном клиенте, действует на другом.

---

## 4. Только веб и только приложение

Часть функций существует только на одном клиенте — это исключения, а не
расхождение.

| Только веб | Почему |
|---|---|
| Админка суперадмина, реклама, экран ёмкости | Служебные инструменты оператора платформы на отдельных поддоменах; в приложение не переносятся |
| Лендинг, SEO-страницы, sitemap | Нужны поисковикам, а не пользователю приложения |

| Только приложение | Почему |
|---|---|
| Сплеш с автоматическим входом | На сайте его роль выполняет страница входа |
| Режим «нет сети» | Сайт без сети не открывается вовсе |
| Push-уведомления, фоновое аудио | Возможности устройства; на сайте — Web Push, если он появится |
| Съёмка с камеры телефона, захват по NDI | Возможности устройства (FR-50, FR-51) |
| Хранение сессии в защищённом хранилище устройства | На сайте — HttpOnly cookie |

Новое исключение добавляется в эту таблицу явно; всё, чего в ней нет,
должно быть на обоих клиентах.
