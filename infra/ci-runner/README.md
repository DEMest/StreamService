# Self-hosted runner для CI

Прогоняет `.github/workflows/ci.yml` на своём сервере вместо хостовых раннеров
GitHub. Причина перехода: хостовые раннеры перестали выдаваться
(`The job was not acquired by Runner of type hosted even after multiple
attempts`), джобы висели в очереди и отменялись.

Побочные выгоды: минуты Actions не тратятся вообще (лимит приватных
репозиториев на self-hosted не распространяется), а `pnpm store` живёт на томе
между прогонами.

## Запуск

1. GitHub → Settings → Actions → Runners → **New self-hosted runner** → Linux.
   Со страницы нужен только токен из строки `./config.sh --token ...`.
   **Токен живёт 1 час.**

2. Создать `infra/ci-runner/.env`:

   ```
   REPO_URL=https://github.com/DEMest/StreamService
   RUNNER_TOKEN=<токен со страницы>
   ```

3. ```bash
   cd infra/ci-runner
   docker compose up -d --build
   docker compose logs -f          # ждём "Listening for Jobs"
   ```

Раннер появится в Settings → Actions → Runners со статусом Idle.

После первого запуска токен больше не нужен: раннер держит собственные
учётные данные на томе `runner-work`. Строку `RUNNER_TOKEN` из `.env` можно
удалить — при перезапуске регистрация пропускается.

## Один раннер = джобы идут по очереди

`api` и `web` описаны как параллельные, но один раннер берёт за раз один джоб,
поэтому фактически они выполнятся последовательно: примерно 2 минуты каждый,
около 4–5 минут на прогон вместо 2–3. На хостовых раннерах они шли параллельно.

Если это станет мешать, поднимите второй раннер с другим именем — оба возьмут
по джобу:

```bash
RUNNER_NAME=streamservice-ci-2 docker compose -p ci-runner-2 up -d
```

Имя обязано быть уникальным: при совпадении `--replace` затрёт регистрацию
первого, и раннер останется один.

## Изоляция

Раннер выполняет содержимое workflow **из любой ветки репозитория**. На этой
машине рядом живут продовые секреты, поэтому:

- хостовых монтирований нет ни одного — каталог проекта и `.env` недоступны;
- докер-сокет не проброшен — управлять контейнерами прода раннер не может;
- работает от непривилегированного пользователя `runner`;
- потолок 8 CPU и 8 ГБ — параллельный jest не отбирает процессор у
  транскодеров FFmpeg, иначе у зрителей рассыпается HLS.

Ограничение, которое это накладывает: workflow **не может** собирать docker-образы
и поднимать сервисные контейнеры. Если такое понадобится, нужен отдельный
раннер с сокетом — и тогда изоляцию надо продумывать заново, а не проковыривать
дырку в этом.

## Обслуживание

```bash
docker compose logs -f              # что делает раннер
docker compose restart              # после зависшего джоба
docker compose down                 # снимает регистрацию (см. trap в entrypoint)
docker compose up -d --build        # обновить версию раннера
```

Раннер обновляет себя сам, но при сильном отставании GitHub перестаёт выдавать
ему джобы — тогда поднимите `RUNNER_VERSION` в `.env` и пересоберите.

Если сервер выключен, CI не работает: проверки на PR останутся в очереди.
Это осознанная цена отказа от хостовых раннеров.
