# Перенос Compose в Kubernetes

На стенде проверяем миграцию на копиях PostgreSQL и MinIO. Публичный трафик
переключается после отдельной проверки данных и выделенного окна.

1. Поднять кандидат на другом адресе, где порты не пересекаются с Compose.
   Проверить Ingress со всеми именами, TLS, SRT/RTMP и доступ к MinIO. Подготовить
   тома по текущему объёму и запасу на эфир, проверить доступ к реестру и
   применить секреты из защищённого хранилища. Если Timeweb использует
   внешний nginx, сначала настроить его маршрут к новому Web и проверить
   исключение приватного HLS и архива. Перенести `LIVE_HLS_CDN_ORIGIN` и
   `LIVE_HLS_CDN_STREAM` в ConfigMap приложения после проверки источника.
2. Отрепетировать восстановление. Снять логический дамп через `pg_dump -Fc`,
   восстановить в отдельную пустую базу через `pg_restore --exit-on-error`.
   Для MinIO скопировать бакет через `mc mirror`, сверить список ключей,
   размеры и контрольные суммы контрольных записей. Эфирный HLS создаётся заново.
   Незакрытые Broadcast и незагруженные записи должны завершиться до смены узла.
3. В окно остановить вход, API и обработчики записи на Compose. Зафиксировать
   состояние исходных контейнеров и DNS. Снять финальный дамп и повторить
   копирование, убедиться, что источник больше не принимает запись. Восстановить
   данные в Kubernetes до запуска production API. Проверить миграции,
   вход в кабинет, чат и воспроизведение архива.
4. До переключения DNS подать синтетический SRT и RTMP, проверить HLS и готовую
   запись в MinIO. Затем перенести HTTP и входящие потоки. Проверить
   воспроизведение через Timeweb и контрольный эфир с внешней сети.
5. Пока Kubernetes не принял реальные записи, откат — остановить кандидат,
   вернуть DNS и запустить исходный стек. После начала записи в Kubernetes
   сначала заморозить приём и перенести новые изменения БД и архива обратно.
   Сохранять одного активного писателя на протяжении всей операции.

На одноузловом кластере API остаётся в одном экземпляре из-за чата, фоновых
задач и локальных блокировок. Распределение эфиров между серверами требует
назначения узла в приложении и отдельной обработки архивов на стороне ingest.

## Обновление MediaMTX

MediaMTX хранит пути приёма в памяти. В окно без эфиров сначала дождись нового
MediaMTX, затем перезапусти API, даже если его образ в этом релизе не меняется.
API на старте восстанавливает пути из PostgreSQL.

```bash
kubectl -n streamservice rollout status deployment/mediamtx
kubectl -n streamservice rollout restart deployment/api
kubectl -n streamservice rollout status deployment/api
kubectl -n streamservice exec deployment/mediamtx -- \
  curl -fsS http://127.0.0.1:9997/v3/config/paths/list
```

Сверь число и имена путей с базой на сервере. Ответ содержит конфигурацию
приёма, поэтому не публикуй его в журналах CI. Проверь SRT и RTMP перед
возвратом эфиров. При аварийной замене пода MediaMTX выполнить те же шаги.
